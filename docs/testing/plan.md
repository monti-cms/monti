# 테스트 개편 방향

소유자와 정한 방향이다(2026-10-30). 개편은 이 방향대로만 한다. 규칙의 자세한 내용은 [`testing.md`](../testing.md), 기능의 중요도는
[`features.md`](features.md), 다른 CMS와 견준 조사는 [`peers-2026-10.md`](peers-2026-10.md)에 있다.

## 목표

결함을 잡는 테스트를 적은 비용으로 둔다. 테스트 수는 목표가 아니다. Monti의 테스트 양은 비슷한 CMS의 중간 정도이고(소스 1천 줄당 36개,
중간값 32개), 문제는 양이 아니라 질과 배치였다.

## 층마다 맡는 일

같은 것을 두 층에서 검사하지 않는다. 경우의 수는 아래 층이, 이어짐은 위 층이 맡는다.

| 층 | 무엇을 검사하나 | 서버와 DB | 어디에 |
|---|---|---|---|
| L1 로직 | 규칙과 판단의 모든 경우. 화면이 내리는 판단(무엇을 보이고 무엇을 보낼지)도 함수로 뽑아 여기서 본다 | 없음 | 코드 옆 `__test__` |
| L2 통합 | core는 데이터가 맞게 저장·삭제·복원되는지를 실제 Postgres로 본다. HTTP 라우트는 권한, 상태 코드, 요청과 응답의 모양만 본다 | 실제 DB | 코드 옆 `__test__` |
| L3 화면 조각 | 사용자의 동작이 올바른 요청이나 콜백이 되는지, 상태가 화면에 보이는지. 동작이 까다로운 부품(메뉴, 편집기, 폼)에 둔다. 경우의 수는 L1에 맡긴다 | 한곳에서 만든 가짜 API. core의 실제 응답 모양에서 만든다 | 코드 옆 `__test__` |
| L4 흐름 | 🔴 흐름마다 하나. 실제 브라우저, 서버, DB로 흐름이 끝까지 이어지는지만 본다. 예외 경우는 아래 층이 본다 | 실제 | 흐름 폴더 한곳 |
| 모양 | 꼭 필요한 화면 몇 개. 고정된 환경과 배포용 빌드에서, 작은 허용 오차로 찍는다 | | 마지막에 한다 |

L4는 PR마다 돈다. 재시도는 하지 않는다. 실패하면 그 테스트나 앱을 고친다.

## 남기고 지우는 기준

기능 하나마다 요구사항을 적고(🔴 기능은 빠짐없이, 🟡 기능은 핵심만, ⚪ 기능은 적지 않는다), 요구사항마다 그것을 잡을 수 있는 가장 낮은
층에 테스트 하나를 둔다. 어느 요구사항에도 짝이 없는 테스트는 지운다. 🔴 요구사항에 짝이 없으면 테스트를 더한다.

## 금지

`testing.md`의 금지 목록을 따른다. 약한 검사(`toBeTruthy`, `toBeDefined`), 클래스 이름, 테스트 id, CSS 선택자, 고정 sleep, 자기 모듈 mock,
블로그 이름, 그리고 화면 테스트에서 `fetch`를 직접 바꿔 끼우는 것이다. 패키지를 정리할 때마다 그 패키지의 상한을 `pnpm check:tests`가 막는다.

## 순서

1. **admin의 약한 검사를 고친다.** `toBeTruthy`·`toBeDefined`, 클래스 이름, 테스트 id, CSS 선택자를 실제 값과 역할로 바꾼다(core 1단계와 같은 일).
2. **화면과 서버의 경계를 바로잡는다.** admin의 가짜 API를 한곳에 만들고, `fetch`를 직접 바꾸던 테스트가 그것을 쓰게 한다.
3. **판단을 함수로 뽑는다.** L3가 경우마다 보던 판단을 L1으로 내리고, 겹치는 L3를 지운다.
4. **🔴 흐름마다 L4를 둔다.** 아래 층이 탄탄해진 뒤에 한다.
5. **시각 회귀를 작게 다시 짠다.** 소유자와 함께 한다.
6. **나머지 패키지**(mdx, ai, blocks, ui와 작은 패키지들)에 1단계를 한다.

## 패키지가 끝났다는 기준

- 금지 패턴이 CI 상한(`pnpm check:tests`) 아래에 있다.
- 🔴 기능의 요구사항 표가 모두 채워져 있다.
- 순서를 섞어 돌려도, 여러 번 돌려도 결과가 같다.

## 보고

PR마다 테스트 수와 실행 시간의 전후, 걸린 작업 시간을 적는다. 패키지 하나가 끝나면 멈추고 소유자에게 보고한다.
그 사이에는 묻지 않고, CI가 통과하면 합친다.
