# 다른 CMS는 테스트를 어떻게 하나 (2026년 10월 조사)

Monti의 테스트 개편 방향을 잡으려고, TypeScript·JavaScript로 된 오픈소스 CMS 9개의 저장소를 받아 Monti와 같은 방법으로 셌다.
Payload, Keystatic, TinaCMS, Directus, Strapi, Sanity, Keystone, Decap CMS, Ghost다(2026-10-30의 기본 브랜치, `--depth 1`).
받은 코드는 실행하지 않고 파일만 읽었다. 숫자는 이름 규칙과 정규식으로 센 어림이라, 프로젝트끼리 견주는 데만 쓴다.

## 얼마나 많나

소스(테스트, 예제, 빌드 결과, 빈 줄과 주석을 뺀 줄)와 테스트 파일에 적힌 `it(`·`test(` 수를 셌다.

| | 소스(천 줄) | 테스트 수 | 1천 줄당 테스트 | 테스트 코드 / 소스 코드 |
|---|---|---|---|---|
| Keystatic | 91 | 1,032 | 11 | 0.34 |
| Keystone | 39 | 1,000 | 26 | 0.88 |
| Payload | 330 | 8,870 | 27 | 0.70 |
| Sanity | 328 | 9,213 | 28 | 0.66 |
| Decap CMS | 71 | 2,300 | 32 | 0.56 |
| **Monti** | **128** | **4,622** | **36** | **0.67** |
| TinaCMS | 109 | 4,124 | 38 | 0.63 |
| Directus | 230 | 10,850 | 47 | 0.78 |
| Strapi | 275 | 13,832 | 50 | 1.12 |
| Ghost | 447 | 25,256 | 57 | 1.16 |
| 9개의 중간값 | | | 32 | 0.70 |

Monti의 테스트 양은 평범하다. 처음 본 "약 7,000개"는 실행 횟수였다. 같은 테스트를 다른 사이트 설정으로 한 번 더 돌리고 표 테스트를 펼친 수다.
테스트가 많아서 생긴 문제가 아니라 테스트의 질 문제였다.

## 어느 층에 있나

테스트 파일마다 쓰는 것으로 층을 갈랐다. 브라우저 흐름(L4)은 Playwright·Cypress나 `e2e` 폴더, 화면 렌더(L3)는 Testing Library·jsdom,
DB·서버(L2)는 데이터베이스나 서버를 띄우는 도구, 나머지가 로직(L1)이다. 테스트 수의 비율이다.

| | L1 로직 | L2 DB·서버 | L3 화면 렌더 | L4 브라우저 흐름 |
|---|---|---|---|---|
| **Monti** | 55% | 22% | **23%** | **0%** |
| 9개의 중간값 | 63% | 14% | 14% | 2% |
| Payload | 60% | 14% | 0% | 26% (133개 파일) |
| Ghost | 73% | 14% | 7% | 5% (190개 파일) |
| Strapi | 66% | 23% | 10% | 2% (102개 파일) |

9개 중 7개가 브라우저나 실제 서버로 흐름을 끝까지 돌리는 테스트를 둔다. Monti는 그 자리를 jsdom 화면 테스트가 대신해서 L3가 많다.
Directus의 `e2e` 폴더는 브라우저가 아니라, 띄운 서버에 HTTP로 요청하는 API 테스트다.

## 1. 화면과 서버 사이는 어떻게 테스트하나

화면을 렌더하는 테스트 파일이 서버를 어떻게 다루는지 셌다.

| | 화면 테스트 파일 | 서버를 다루지 않음(속성만 넘김) | API 모듈을 mock | 가짜 서버(MSW) | fetch를 직접 바꿔 끼움 |
|---|---|---|---|---|---|
| **Monti** | 115 | 65% | 0% | 0% | **35%** |
| Sanity | 379 | 69% | 29% | 0% | 2% |
| Ghost | 238 | 70% | 24% | 5% | 3% |
| Directus | 195 | 76% | 24% | 0% | 1% |
| Strapi | 172 | 58% | 27% | 18% | 1% |
| Keystatic, Keystone, Decap | | 100% | | | |

- 다른 프로젝트의 화면 테스트는 대부분 서버 없이 속성만 넘겨 화면 조각을 본다. 서버가 필요하면 API 모듈을 통째로 바꾸거나 MSW를 쓴다.
- 서버 자체는 실제로 띄운 앱에 요청하는 테스트로 따로 지킨다. Strapi는 `tests/api`(289개 파일, 실제 Strapi 인스턴스), Directus는
  `tests/e2e`(98개 파일, Docker의 7가지 DB로 같은 테스트), Payload는 기능 폴더마다 `int.spec.ts`(REST 클라이언트로 실제 DB에 요청)다.
- Monti의 admin 화면 테스트는 35%가 `fetch`를 직접 바꿔 끼워 서버 응답을 손으로 흉내 낸다. 응답 모양이 실제와 어긋나도 알 수 없다.
- Directus의 테스트 안내는 단위 테스트를 먼저 쓰고, 단위 테스트가 다루는 것을 상위 테스트에서 다시 검사하지 말며, 상위 테스트는
  큰 흐름이 이어지는지 확인하는 데 쓰라고 한다.

## 2. 브라우저 흐름 테스트는 어떻게 돌리나

- **언제**: 브라우저 흐름 테스트가 있는 프로젝트는 모두 PR마다 돌린다. 여러 조각으로 나눠 동시에 돌린다(`--shard`).
- **재시도**: 대부분 CI에서 실패하면 두 번까지 다시 돌린다(`retries: 2`). Ghost의 본 흐름 테스트는 재시도를 꺼 두었다. 재시도가 필요하면
  테스트가 나쁘거나 앱이 고장 난 것이라는 이유다. Sanity는 불안정한 테스트를 따로 모아 보고하는 작업을 정해진 시간마다 돌린다.
- **구성**: Payload는 테스트를 기능 폴더로 묶는다(`test/<기능>/int.spec.ts`와 `e2e.spec.ts`, `e2e.spec.ts`가 있는 기능 폴더 107개).
  흐름 테스트 파일 하나에 테스트가 평균 17개쯤으로, 정상 경로만이 아니라 여러 경우를 브라우저에서 본다. Ghost는 파일당 7개쯤이다.

## 3. 테스트 데이터와 격리

| | 방식 |
|---|---|
| Payload | 테스트 묶음마다 DB를 지우고 씨앗 데이터를 넣은 뒤 스냅숏을 떠 두고, 다음부터는 스냅숏으로 되돌린다(`seedDB`). 같은 통합 테스트를 MongoDB, Postgres, SQLite, Supabase 등 여러 DB 설정으로 돌린다 |
| Strapi | 테스트 파일마다 필요한 콘텐츠 타입과 데이터를 선언해 만들고, 끝나면 지운다(`createTestBuilder`, 414번 쓰임). SQLite, Postgres, MySQL, MariaDB로 돈다 |
| Keystone | 테스트마다 그 테스트의 설정으로 앱을 새로 만든다(`setupTestRunner`, 135번) |
| Ghost | 이름 붙은 고정 데이터 묶음을 테스트 파일이 골라 넣는다(`testUtils.setup('users', 'posts')`, `fixtureManager`) |
| Directus | 띄운 서버 하나를 여러 테스트가 같이 쓰고, 무거운 테스트만 자기 서버(샌드박스)를 띄운다 |
| **Monti** | 테스트(또는 파일)마다 Postgres 스키마를 새로 만든다. 저장소 계약 테스트(어떤 저장소든 지켜야 할 동작)를 Postgres 어댑터에 돌린다 |

여러 DB를 같은 테스트로 검사하는 Payload·Strapi·Directus의 방식은 Monti의 저장소 계약 테스트와 같은 발상이다.

## 4. 시각 회귀

9개 중 4개에서 시각 회귀 도구를 찾았다.

- **Payload**: 스크린샷 검사가 3개 파일에서 6번뿐이다. 고정된 Playwright Docker 이미지에서만 기준 이미지를 만들고, 배포용 빌드에서만 찍고,
  글꼴 로딩을 기다리고 애니메이션을 끈 뒤, 픽셀 1%까지 차이를 허용한다(`maxDiffPixelRatio: 0.01`).
- **Decap CMS**: Cypress 이미지 스냅숏, 1% 허용.
- **Sanity**: Chromatic(Storybook 스크린샷을 비교하는 외부 서비스). PR에 라벨을 붙였을 때만 돌린다.
- **Ghost**: Chromatic 설정이 있다. 어떻게 돌리는지는 확인하지 않았다.
- **Monti**: Storybook 화면 75개를 픽셀 차이 없이 비교한다. 1px 차이로 기준 이미지를 다시 커밋하게 된 원인이다.

## 5. 애매한 안티 패턴

테스트 1천 개당 몇 번 나오는지다.

| | 클래스 이름 | CSS 선택자 | 테스트 id | 스냅숏 | 위치로 읽는 mock 인자 | `toBeTruthy`·`toBeDefined` | 고정 sleep | 자기 모듈 mock |
|---|---|---|---|---|---|---|---|---|
| **Monti 전체** | 6.3 | 27.4 | 28.7 | 0 | 10.1 | **92.1** | 2.6 | 8.2 |
| Monti core | 3.7 | 0 | 0 | 0 | | 0 | | |
| **Monti admin** | **15.0** | **72.9** | **85.1** | 0 | | **243.7** | | |
| 9개의 중간값 | 1.8 | 21.3 | 41.7 | 11.2 | 16.0 | 41.2 | 3.9 | 9.7 |

core는 1단계에서 정리해서 깨끗하다. admin은 아직 1단계를 하지 않아, "있기만 하면 통과"하는 검사가 중간값의 6배이고 클래스 이름 검사는 8배다.
스냅숏은 Monti가 쓰지 않는다. Keystatic(1천 개당 363)과 Keystone(190)은 많이 쓴다.

## 6. 테스트를 어디에 두나

| | 코드 옆 | 한곳에 모은 테스트 폴더 | 흐름 테스트 폴더 |
|---|---|---|---|
| **Monti** | 100% | 0% | 0% |
| Payload | 56% | 39% (기능 폴더별) | 5% |
| Ghost | 24% | 68% | 8% |
| Keystone | 22% | 78% | 0% |
| Strapi | 74% | 20% | 6% |
| Sanity | 81% | 13% | 6% |

로직 테스트는 대부분 코드 옆에 둔다. 서버를 띄우는 통합 테스트와 흐름 테스트는 한곳(기능 폴더)에 모으는 프로젝트가 많다.

## 7. 어느 방향에서 검증하나

| | 사용자가 보는 것으로 찾기(역할, 이름표, 글자) | "불렸나"를 확인하는 검사의 비율 |
|---|---|---|
| **Monti** | 90% | 5% |
| 9개의 중간값 | 65% | 11% |

Monti는 화면 요소를 사용자가 보는 것으로 찾고, 함수가 불렸는지보다 결과 값을 확인한다. 이 방향은 다른 프로젝트보다 낫다.

## Monti가 할 일

1. **admin에 1단계를 한다.** `toBeTruthy`, 클래스 이름, 테스트 id, CSS 선택자를 실제 값과 역할로 바꾼다. 가장 큰 질의 차이다.
2. **화면과 서버의 경계를 바로잡는다.** admin 테스트가 `fetch`를 직접 흉내 내는 대신, core의 실제 응답 모양에서 만든 가짜 응답을 한곳에서 쓴다.
3. **판단을 함수로 뽑는다.** jsdom 화면 테스트가 경우마다 보던 판단을 로직 테스트로 내려 L3를 줄인다.
4. **🔴 흐름마다 브라우저 흐름 테스트를 둔다.** 아래 층이 탄탄해진 뒤에, 흐름이 끝까지 이어지는지를 본다. 기능 폴더 하나에 모은다(Payload 방식).
5. **시각 회귀는 작게 다시 짠다.** 꼭 필요한 화면만, 고정된 Docker 환경과 배포용 빌드에서, 작은 허용 오차로 찍는다.
