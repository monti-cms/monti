# 요구사항: 데이터베이스

상태: 초안 (2026-10-31).

중요도: [기능의 중요도](../features.md)의 "데이터베이스 연결과 마이그레이션" 🔴(제안대로, 2026-10-31). `monti db:setup`과 `monti db:migrate`,
연결 설정 읽기, 다른 앱의 표나 다른 사이트의 데이터베이스에 쓰지 않는 것이다. 흐름이 따로 없다. 명령의 출력에 비밀번호가 없는 것은
[명령줄](cli.md)의 CLI-P2, 설치 실수를 알리는 말은 [처음 설치와 로그인](first-install.md)의 SETUP-E1, 플러그인의 마이그레이션은
[관리자 플러그인](plugins.md)의 PLUG-S8, 인스턴스가 언제 연결하는지는 [설정 파일과 인스턴스](config.md)의 CONF-I1이 다룬다.
읽는 법은 [휴지통](trash.md#읽는-법)과 같다.

## 마이그레이션 🔴

| ID | 약속 | 틀리면 | 출처 | 층 |
|---|---|---|---|---|
| DB-M1 | `db:setup`은 빈 데이터베이스에 스키마와 Monti의 표를 만든다. 이미 만든 데이터베이스는 바꾸지 않고 `db:migrate`를 가리킨다. 다른 앱의 표가 있는 스키마에서는 Monti의 표만 더하고 그 표와 행은 건드리지 않는다 | 함께 쓰는 데이터베이스의 다른 앱 데이터가 사라진다 | 코드 · 소유자 확인 (2026-10-31) | L2 |
| DB-M2 | `db:migrate`는 `db:setup` 전이면 아무것도 만들지 않고 `db:setup`을 가리키며 1로 끝난다. 마이그레이션이 실패하면 1로 끝나고 연결을 닫는다 | 반쯤 만든 데이터베이스가 남거나, 실패한 배포가 성공으로 보인다 | 코드 · 소유자 확인 (2026-10-31) | L2 |
| DB-M3 | 마이그레이션은 빠진 단계만 한 번씩 돌린다. 다시 돌려도, 두 곳에서 동시에 돌려도 단계와 처음 데이터를 한 번만 적는다. 적용한 단계의 이름은 바뀌지 않는다(이 부분은 CI의 `pnpm check:migrations`가 지킨다) | 업그레이드할 때 단계가 두 번 돌아 데이터가 겹치거나 지워진다 | 코드 · 소유자 확인 (2026-10-31) | L2 |
| DB-M4 | 마이그레이션은 이전 판에서 쓴 글에 새 판이 기대는 값(번역 비교에 쓰는 해시)을 채운다 | 업그레이드한 사이트의 옛 번역이 "원문 바뀜" 거르기에서 틀리게 나온다 | 코드 · 소유자 확인 (2026-10-31) | L2 |
| DB-M5 | 예전 시험판의 번호 단계로 만든 데이터베이스는 올리지 않고, 아무것도 바꾸지 않은 채 다시 만들라고 알린다 | 맞지 않는 표 위에 단계를 돌려 데이터를 망가뜨린다 | 코드 · 소유자 확인 (2026-10-31) | L2 |
| DB-M6 | 설정에 `schema`만 정하고 마이그레이션을 돌리면 그 스키마를 만든다 | 첫 설치가 스키마가 없다는 오류로 멈춘다 | 코드 · 소유자 확인 (2026-10-31) | L2 |

## 연결 🔴

| ID | 약속 | 틀리면 | 출처 | 층 |
|---|---|---|---|---|
| DB-C1 | 연결은 `DATABASE_URL`과 `DATABASE_SCHEMA`(없으면 `public`)에서 읽고, 설정에 쓴 값이 이긴다. 다른 변수에서 짐작하지 않는다. 빠진 변수는 처음 연결할 때 그 이름, 자리, 고치는 법으로 알리고, SQL에 쓸 수 없는 스키마 이름은 거부한다 | 엉뚱한 데이터베이스나 스키마에 쓰거나, 사이트가 이유를 말하지 않고 시작하지 않는다 | 코드 · 소유자 확인 (2026-10-31) | L1 |
| DB-C2 | 명령줄은 env 파일로 셸에 있는 값을 덮지 않는다. 셸, `.env.local`, `.env` 순으로 앞의 것이 이긴다 | 셸에서 고른 데이터베이스 대신 `.env`의 데이터베이스에 명령이 돈다 | 코드 · 소유자 확인 (2026-10-31) | L2 |
| DB-C3 | 인스턴스는 자기 서버 설정의 데이터베이스에만 쓰고, `migrate`와 `close`도 자기 데이터베이스에만 한다. 데이터베이스 어댑터에는 자기 사이트를 넘긴다. 개발이 아니면 다른 인스턴스와 연결을 나눠 쓰지 않는다 | 한 사이트의 글이 다른 사이트의 데이터베이스에 쓰이거나, 다른 사이트의 스키마로 마이그레이션한다 | 코드 · 소유자 확인 (2026-10-31) | L1 |
| DB-C4 | 연결과 표의 오류를 설명하는 말에는 데이터베이스의 사용자와 비밀번호가 없다 | 첫 요청의 오류 기록에 데이터베이스 비밀번호가 남는다 | 코드 · 소유자 확인 (2026-10-31) | L1 |

## 찾은 것

### 약속 없는 테스트 나누기 (2026-10-31)

- `kysely.int`의 테스트 16개(트랜잭션 도우미, 연결 빌려주기, 제목 식의 SQL)는 기능이 아니라 배관이라 세부다. 같은 결함을 발행, 스키마 변경,
  복원의 되돌림과 폴더 동시성 테스트가 동작으로 잡는다. 지우기 전에 `store/context.ts`와 `db/kysely.ts`를 변이 테스트로 잰다.
- `database-types.int`의 소스를 읽는 테스트 8개는 지웠다(#378). 이제 `db/database.ts`는 `pnpm gen:db-types`가 새로 마이그레이션한 스키마에서
  만들고, CI(테스트 1번 조각)의 `pnpm gen:db-types --check`가 파일과 마이그레이션이 다른 표와 열을 이름 대며 막는다. 생성기가 읽지 못하는
  이름 붙은 타입과 열 설명은 `scripts/db-columns.ts`에, 값 타입(`Jsonb`, `Int8`, `BigSerial`)은 `db/column-types.ts`에 손으로 쓴다.
- `migrations.int`의 "has exactly the baseline as its step list"(DB-M3)는 손으로 적은 목록이라 지웠다(#378). CI(`check` 작업)의
  `pnpm check:migrations`가 기준 가지에 있던 단계 파일(`NNNN_이름.ts`)의 이름 바꿈과 지움을 막고, 단계 목록이 단계 파일과 같은지 본다.
  단계를 더하는 것은 된다.
