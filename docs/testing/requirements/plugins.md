# 요구사항: 관리자 플러그인

상태: 초안 (2026-10-31).

중요도: [기능의 중요도](../features.md)의 "플러그인 API" 🟡. 플러그인이 관리자 화면에 더하는 것(`defineAdminPlugin`: 페이지, 컴포넌트, 슬롯,
상태 줄의 칸, 옆 패널, 블록 보기, 목록 칸, 글자 꾸밈, 글자 검사기)과 플러그인에게 공개한 훅이다. 🟡라서 대표 약속만 적는다. 서버 쪽 훅(검사, 커밋 전후)은
[글 쓰고 발행](write-and-publish.md)의 WRITE-H1~H3, 형식 플러그인은 [본문 형식](body-format.md)의 FMT-P1이 다룬다. 목록 칸(`listCells`)은
목록의 LIST-S3(⚪)에서 이 표로 옮겼다(제안대로, 2026-10-31). 읽는 법은 [휴지통](trash.md#읽는-법)과 같다.

## 글자 검사 🟡

플러그인은 2026-10-28에 core 밖으로 나갔다) 약속을 받는 쪽이 플러그인 작성자다. 그래서 이 표에 둔다.

## 서버 쪽 🟡

플러그인이 서버에 더하는 것(라우트, 명령, 기능 값, 커밋 뒤 구독자, 마이그레이션, 옵션)이다. [기능의 중요도](../features.md)의 "서버 쪽 플러그인 API"
🟡(제안대로, 2026-10-31)라서 대표 약속만 적는다. 플러그인 라우트를 관리자만 부르는 것은 [관리자 API](api.md)의 API-G1, 쓰기 훅은 WRITE-H1~H4,
형식은 FMT-P1, 이벤트 전송은 [활동 기록](events.md)의 EVENT-D1~D4, 키 칸은 [API 키](keys.md)의 KEY-P1, core의 저장 범위 이름(`auth`,
`core-keys`)을 막는 것은 KEY-S1이 다룬다.

| ID | 약속 | 틀리면 | 출처 | 층 |
|---|---|---|---|---|
| PLUG-S1 | 플러그인 라우트는 `cms.handle`로 닿고, 자기를 부른 인스턴스와 플러그인 문맥을 받는다. `signed` 라우트는 라우터가 로그인을 보지 않고 라우트가 서명을 본다 | 한 사이트의 플러그인 라우트가 다른 인스턴스의 데이터를 읽거나, 웹훅이 모두 401이 된다 | 코드 | L1 |

| PLUG-S6 | 플러그인의 서버 콜백(라우트, 기능 값, 커밋 뒤 구독자, 마이그레이션)은 그 인스턴스와 그 플러그인의 문맥을 받는다. 문맥(`cms.plugin(name)`)은 그 이름의 저장소, 비밀값, 키 저장소를 주고, `once(key, make)`는 플러그인과 키마다 값을 한 번 만들며 스키마를 다시 읽으면 새로 만든다 | 플러그인이 다른 플러그인의 저장소를 받거나, 스키마를 고친 뒤에도 옛 컬렉션으로 일한다 | 코드 | L1 |
| PLUG-S7 | 커밋 뒤 구독자는 서버 설정의 것 다음에 플러그인 순서로 받는다. 이름 `<주인>:<이름>`이 전송 상태의 키이고, 적힌 종류만 받으며 `changed`는 모든 종류를 받는다. 잘못된 이름과, 한 주인 안의 같은 이름(종류가 달라도)은 거부한다 | 발행 알림이 저장마다 가거나, 같은 이름의 두 구독자가 전송 상태를 나눠 하나가 받지 못한다 | 코드 | L1 |
| PLUG-S8 | `monti db:migrate`는 core 표 다음에, `migrate`가 있는 플러그인마다 설정 순서로 돈다. 플러그인의 한 번만 도는 단계는 동시에 불려도 한 번이고, 플러그인마다 따로 세며 core 마이그레이션 기록에 그 플러그인의 이름으로 남는다. 실패한 단계는 쓴 것을 남기지 않고 다음에 다시 돈다 | 플러그인 표가 없거나, 플러그인의 데이터 옮기기가 두 번 돌거나 반쯤 남는다 | 코드 | L2 |

## 플러그인 저장소 🔴

플러그인이 저장하는 문서다. 로그인의 관리자 계정과 API 키 저장소도 여기에 있다. 메모리 저장소와 Postgres가 같은 계약
(`plugin/__test__/storage-contract.ts`)을 지킨다. [기능의 중요도](../features.md)의 "플러그인 저장소" 🔴(제안대로, 2026-10-31).
