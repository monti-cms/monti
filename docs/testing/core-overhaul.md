# Core 테스트 정비 기록

[`testing.md`](../testing.md)의 규칙으로 core의 테스트를 정비한 기록이다. 단계마다 [기준점](baseline-2026-10.md)과 같은 스크립트로 다시 잰다.
남은 단계는 이슈 #341에 있다.

## 1단계: 테스트가 저마다 홀로 서고 동작을 검사한다

테스트 파일 73개를 고쳤다.

- 앞선 테스트가 남긴 것을 읽던 테스트가 자기 데이터를 만든다.
- `toBeDefined`, `toBeTruthy`, 위치로 읽는 mock 호출 인자, 고정 sleep, 두 언어 정규식 대신 실제 값을 검사한다.
- 참조 블로그의 이름 대신 사이트 설정에서 이름을 찾는다.
- `pnpm check:tests`가 CI에서 core에 새 약한 패턴과 블로그 이름이 들어오는 것을 막는다(아래 표의 1단계 뒤 숫자가 상한).

| 지표 | 기준점 | 1단계 뒤 |
|---|---|---|
| 테스트가 순서에 기대는 파일 | 18 | 0 (테스트 순서를 6가지로 섞어 돌려 모두 통과) |
| 약한 패턴 | 119 | 10 |
| 참조 블로그 이름 | 37개 파일에서 103회 | 10개 파일에서 24회 |
| 테스트와 시간 | 테스트 3,515개, 89초 | 테스트 3,561개, 87초 (세 번 잰 중간값, 86–91초) |
| 커버리지(줄 / 분기 / 함수) | 94.7 / 84.0 / 94.0% | 94.7 / 84.0 / 94.0% |
| 변이 점수 | 66.3% (23,036 / 34,747), 가짜 잡기를 뺀 값 | 66.4% (23,055 / 34,747) |
| 찾아서 고친 결함 | — | 2 (#340) |

시간과 커버리지는 그대로다. 1단계는 이 둘을 바꾸려는 단계가 아니다. 테스트가 46개 는 것은 다른 사이트 설정으로도 도는 테스트가 늘었기
때문이다. 블로그 이름 대신 설정에서 이름을 찾으니, 전에는 다른 사이트에서 건너뛰던 테스트가 돈다.

변이 점수는 처음 잰 기준점(68.8%)과 견주면 떨어진 것처럼 보인다. 떨어진 만큼은 순서에 기대던 테스트의 가짜 잡기였고, 하나씩 확인한 내용은
[바로잡은 변이 점수](baseline-2026-10.md#바로잡은-변이-점수)에 있다. 가짜를 빼고 견주면 새로 잡은 변이가 21개, 1단계가 약하게 만든 검사가 1개다.
그 검사는 고쳤다. 다시 잰 뒤에 아무 테스트도 실행하지 않게 된 코드 4곳(새 언어를 diff에 적는 코드)에는 그 동작을 검사하는 테스트를 더했다.
이 다섯 변이는 손으로 넣어 잡히는 것을 확인했고, 위 표의 숫자에는 들어 있지 않다.

1단계 중에 찾은 결함 두 개는 #340에서 고쳤다. 복원 문제가 제목 대신 다른 값을 이름으로 보였고, 없는 대상을 가리키는 참조가 데이터베이스
오류 코드로 새어 나갔다.

### 정비하면서 배운 것

- 하위 에이전트의 보고는 확인 전까지 믿지 않는다. 한 에이전트는 테스트 파일을 실행 결과 JSON으로 덮어쓰고도 성공했다고 보고했다. 파일마다
  테스트 수를 정비 전후로 비교해서 찾았다.
- zsh는 `$VAR` 안의 줄바꿈으로 단어를 나누지 않는다. 파일 58개를 돌린다고 생각했는데 11개만 돌았다. 확인 스크립트가 이제 돈 파일 수를 찍는다.
- 변이 측정 중에는 같은 작업 폴더에서 소스를 고치거나 테스트를 돌리지 않는다. Stryker가 변이를 `src` 파일에 직접 쓰기 때문이다.

## 2단계: 층으로 나누기

파일만 옮기고 테스트는 고치지 않았다. 파일 이름을 가리키는 테스트 하나(`store-contract-files`)와 주석만 새 이름을 따른다.

- L2 테스트 81개가 `.int.test.ts`가 되었다. DB를 쓰는 것 55개, 파일이나 자식 프로세스만 쓰는 것 18개, 소스를 글자로 읽는 것 8개다.
  나머지 158개가 L1이다.
- 층마다 Vitest 프로젝트가 있다. `core`는 L1, `core (int)`는 L2다(`packages/core/vitest.int.config.ts`, 패키지에서는 `pnpm test:int`).
- 여러 폴더가 함께 쓰는 도우미 4개를 `packages/core/test/`로 옮겼다(`paragraphs-format`, `blog-schema`, `import-schema-text`,
  `export-fixture`). 배포되는 `./testing`이 쓰는 도우미(`seed`, `test-database`, `doc-text`)는 `src`에 남는다.
- 작업 이름이던 `review-regressions.blog.test.ts`는 검사하는 것 옆으로 가서 `core/__test__/snapshot.blog.test.ts`가 되었다.
  L1인데 `.integration.test.ts`라는 옛 이름을 가진 파일 3개는 `.test.ts`가 되었다.

층은 추측하지 않고 확인했다. DB 주소를 아무도 듣지 않는 포트로 바꿔 L1 158개를 돌리니 모두 통과했고, DB를 쓴다고 본 55개는 모두 실패했다.
옮기기 전과 뒤의 테스트를 파일과 이름으로 하나씩 맞춰 보니 6,991개가 모두 같았다.

| 지표 | 1단계 뒤 | 2단계 뒤 |
|---|---|---|
| L1만 돌리기 | 할 수 없음 | 158개 파일, 7초, DB 없이 |
| L2만 돌리기 | 할 수 없음 | 81개 파일, 14초 |
| 전체 테스트 | 6,932개 통과, 59개 건너뜀 | 같음 |
| 파일 안의 순서를 섞어 6번 | 모두 통과 | 모두 통과 |

설계 문서의 이름 규칙을 소유자와 함께 고쳤다(2026-10-30). `.tsx`는 JSX를 쓴다는 뜻일 뿐 층을 말하지 않는다. core의 `.test.tsx` 6개는
서버에서 HTML로 렌더하므로 L1이다. L2는 DB만 뜻하던 `.db.test.ts` 대신 `.int.test.ts`이고, L3는 `.dom.test.tsx`와 `.browser.test.tsx`다.
