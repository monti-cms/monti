# Core 테스트 정비 기록

[`testing.md`](../testing.md)의 규칙으로 core의 테스트를 정비한 기록이다. 단계마다 [기준점](baseline-2026-10.md)과 같은 스크립트로 다시 잰다.
남은 단계는 이슈 #341에 있다.

## 1단계: 테스트가 저마다 홀로 서고 동작을 검사한다

테스트 파일 73개를 고쳤다.

- 앞선 테스트가 남긴 것을 읽던 테스트가 자기 데이터를 만든다.
- `toBeDefined`, `toBeTruthy`, 위치로 읽는 mock 호출 인자, 고정 sleep, 두 언어 정규식 대신 실제 값을 검사한다.
- 참조 블로그의 이름 대신 사이트 설정에서 이름을 찾는다.
- `pnpm check:tests`가 CI에서 core에 새 약한 패턴과 블로그 이름이 들어오는 것을 막는다(아래 표의 1단계 뒤 숫자가 상한).

| 지표 | 기준점 | 1단계 뒤 |
|---|---|---|
| 테스트가 순서에 기대는 파일 | 18 | 0 (테스트 순서를 6가지로 섞어 돌려 모두 통과) |
| 약한 패턴 | 119 | 10 |
| 참조 블로그 이름 | 37개 파일에서 103회 | 10개 파일에서 24회 |
| 테스트와 시간 | 테스트 3,515개, 89초 | 테스트 3,561개, 87초 (세 번 잰 중간값, 86–91초) |
| 커버리지(줄 / 분기 / 함수) | 94.7 / 84.0 / 94.0% | 94.7 / 84.0 / 94.0% |
| 변이 점수 | 66.3% (23,036 / 34,747), 가짜 잡기를 뺀 값 | 66.4% (23,055 / 34,747) |
| 찾아서 고친 결함 | — | 2 (#340) |

시간과 커버리지는 그대로다. 1단계는 이 둘을 바꾸려는 단계가 아니다. 테스트가 46개 는 것은 다른 사이트 설정으로도 도는 테스트가 늘었기
때문이다. 블로그 이름 대신 설정에서 이름을 찾으니, 전에는 다른 사이트에서 건너뛰던 테스트가 돈다.

변이 점수는 처음 잰 기준점(68.8%)과 견주면 떨어진 것처럼 보인다. 떨어진 만큼은 순서에 기대던 테스트의 가짜 잡기였고, 하나씩 확인한 내용은
[바로잡은 변이 점수](baseline-2026-10.md#바로잡은-변이-점수)에 있다. 가짜를 빼고 견주면 새로 잡은 변이가 21개, 1단계가 약하게 만든 검사가 1개다.
그 검사는 고쳤다. 다시 잰 뒤에 아무 테스트도 실행하지 않게 된 코드 4곳(새 언어를 diff에 적는 코드)에는 그 동작을 검사하는 테스트를 더했다.
이 다섯 변이는 손으로 넣어 잡히는 것을 확인했고, 위 표의 숫자에는 들어 있지 않다.

1단계 중에 찾은 결함 두 개는 #340에서 고쳤다. 복원 문제가 제목 대신 다른 값을 이름으로 보였고, 없는 대상을 가리키는 참조가 데이터베이스
오류 코드로 새어 나갔다.

### 정비하면서 배운 것

- 하위 에이전트의 보고는 확인 전까지 믿지 않는다. 한 에이전트는 테스트 파일을 실행 결과 JSON으로 덮어쓰고도 성공했다고 보고했다. 파일마다
  테스트 수를 정비 전후로 비교해서 찾았다.
- zsh는 `$VAR` 안의 줄바꿈으로 단어를 나누지 않는다. 파일 58개를 돌린다고 생각했는데 11개만 돌았다. 확인 스크립트가 이제 돈 파일 수를 찍는다.
- 변이 측정 중에는 같은 작업 폴더에서 소스를 고치거나 테스트를 돌리지 않는다. Stryker가 변이를 `src` 파일에 직접 쓰기 때문이다.

## 2단계: 층으로 나누기

파일만 옮기고 테스트는 고치지 않았다. 파일 이름을 가리키는 테스트 하나(`store-contract-files`)와 주석만 새 이름을 따른다.

- L2 테스트 81개가 `.int.test.ts`가 되었다. DB를 쓰는 것 55개, 파일이나 자식 프로세스만 쓰는 것 18개, 소스를 글자로 읽는 것 8개다.
  나머지 158개가 L1이다.
- 층마다 Vitest 프로젝트가 있다. `core`는 L1, `core (int)`는 L2다(`packages/core/vitest.int.config.ts`, 패키지에서는 `pnpm test:int`).
- 여러 폴더가 함께 쓰는 도우미 4개를 `packages/core/test/`로 옮겼다(`paragraphs-format`, `blog-schema`, `import-schema-text`,
  `export-fixture`). 배포되는 `./testing`이 쓰는 도우미(`seed`, `test-database`, `doc-text`)는 `src`에 남는다.
- 작업 이름이던 `review-regressions.blog.test.ts`는 검사하는 것 옆으로 가서 `core/__test__/snapshot.blog.test.ts`가 되었다.
  L1인데 `.integration.test.ts`라는 옛 이름을 가진 파일 3개는 `.test.ts`가 되었다.

층은 추측하지 않고 확인했다. DB 주소를 아무도 듣지 않는 포트로 바꿔 L1 158개를 돌리니 모두 통과했고, DB를 쓴다고 본 55개는 모두 실패했다.
옮기기 전과 뒤의 테스트를 파일과 이름으로 하나씩 맞춰 보니 6,991개가 모두 같았다.

| 지표 | 1단계 뒤 | 2단계 뒤 |
|---|---|---|
| L1만 돌리기 | 할 수 없음 | 158개 파일, 7초, DB 없이 |
| L2만 돌리기 | 할 수 없음 | 81개 파일, 14초 |
| 전체 테스트 | 6,932개 통과, 59개 건너뜀 | 같음 |
| 파일 안의 순서를 섞어 6번 | 모두 통과 | 모두 통과 |

설계 문서의 이름 규칙을 소유자와 함께 고쳤다(2026-10-30). `.tsx`는 JSX를 쓴다는 뜻일 뿐 층을 말하지 않는다. core의 `.test.tsx` 6개는
서버에서 HTML로 렌더하므로 L1이다. L2는 DB만 뜻하던 `.db.test.ts` 대신 `.int.test.ts`이고, L3는 `.dom.test.tsx`와 `.browser.test.tsx`다.

### 소스를 글자로 읽던 테스트를 lint로

소스 파일을 읽어 정규식으로 검사하던 테스트 8개 중 5개가 다루던 규칙을 lint로 옮겼다. 이제 편집기에서 바로 보이고 CI의 `biome check`가 막는다.

| 규칙 | 전 | 후 |
|---|---|---|
| core는 Next를 가져오지 않는다 | `no-next-imports` 테스트 | `biome.json`의 `noRestrictedImports` |
| core는 MDX와 remark 계열을 가져오지 않는다 | `mdx-boundary` 테스트의 소스 검사 | 같은 규칙. 배포되는 `package.json` 검사는 테스트로 남는다 |
| Postgres 어댑터 밖에서는 어댑터, `pg`, Kysely를 가져오지 않는다 | `core/store/import-boundary` 테스트 | 같은 규칙. 파일 묶음마다 허용 범위가 다르다 |
| 제목 필드를 `title` 키로 읽지 않는다 | `title-reads` 테스트 | `biome-plugins/title-key.grit`(GritQL 플러그인) |

옮긴 규칙이 같은 것을 잡는지 확인했다. 파일 종류마다(서비스 코드, 어댑터, 테스트, `test/` 도우미, `testing.ts`, 진단 검사) 금지된 가져오기를
모두 담은 임시 파일을 두고 lint를 돌리니, 원래 테스트가 허용하던 것은 통과하고 막던 것만 걸렸다. 제목 규칙은 원래 테스트가 잡던 모양을
모두 잡고, 링크의 `title`이나 주석은 잡지 않았다. 지금 코드에서는 아무것도 걸리지 않는다.

나머지 3개는 이유를 적어 예외로 두었다(`weak-patterns.mjs`의 `EXEMPT`). `database-types`는 손으로 쓴 DB 타입을 실제 데이터베이스와 견주고,
`store-contract-files`는 계약 묶음마다 그것을 돌리는 테스트 파일이 있는지 보며, `render-css`는 배포되는 스타일시트를 읽는다.
core의 약한 패턴은 10개에서 2개가 되었고, CI 상한도 2로 내렸다.

## 3단계: 살아남은 변이로 빈틈 채우기

처음에는 살아남은 변이를 줄마다 읽고, 테스트를 더하거나 넘기는 이유를 적었다. 휴지통 파일 하나에 몇 시간이 걸렸고 테스트가 30개 늘었다.
이 속도로는 core에만 며칠이 걸리고, 정비의 목표(쓸모없는 테스트를 줄이기)와도 반대로 간다. 그래서 2026-10-30에 소유자와 방향을 바꿨다.
빈틈은 데이터를 쓰는 코드에서만, 아무 테스트도 실행하지 않는 코드와 데이터를 잃게 하는 바꿈만 채운다(`testing.md`의 "빈틈은 중요한 코드에서만
채운다"). 휴지통 테스트 중 지켜도 의미가 적은 것은 4단계에서 덜어낸다.

### 휴지통 (`adapters/postgres/store/trash.ts`)

| 지표 | 전 | 뒤 |
|---|---|---|
| 변이 점수 | 67.3% | 87.5% |
| 아무 테스트도 실행하지 않는 변이 | 64 | 0 |
| 살아남은 변이 | 127 | 74. 그중 8개는 측정 오차라 실제로는 66개, 이어서 3개를 더 잡아 63개 |

테스트를 약 30개 더했다. 휴지통에 없는 것의 영구 삭제 거부, 살아 있는 번역본이 있는 원문 거부, 원문과 함께 지워지는 번역본, 같은
밀리초에 들어간 것끼리 섞이지 않는 시각 도장, 데이터베이스 시계, 여러 단계 폴더 합치기, item 컬렉션 폴더를 되살리면 다시 발행하기 같은 것이다.

**찾아서 고친 결함**: 휴지통 비우기가 앞의 항목과 함께 이미 지워진 것을 "지우지 못함"으로 보고했다. 원문과 따로 휴지통에 든 번역본,
상위 폴더와 함께 지워지는 하위 폴더와 파일이 그랬다. 결과는 목록 순서에 따라 달랐다. 영구 삭제가 한 번의 호출에서 지운 것을 기억하게 고쳤다.

**측정 오차**: 함수 전체를 "아무것도 하지 않음"으로 바꾼 변이 8개는 Stryker가 살아남았다고 기록했지만, 직접 넣어 돌리면 바로 잡힌다.
저장소를 만들 때 정의되는 함수라서 Stryker가 그것을 실제로 부르는 테스트를 고르지 못한다. 점수는 그만큼 실제보다 낮게 나온다.

남은 63개와 이유:

| 이유 | 개수 | 예 |
|---|---|---|
| 개발자만 보는 글자 | 14 | `CmsError`의 영어 메시지 |
| 결과가 같음 | 30 | 빈 목록이면 건너뛰기, 쓰이지 않는 기본값, 저장소가 버리는 `details`, 같은 결과로 끝나는 한 번 더 돌기 |
| 어떤 쓰기도 만들지 않는 상태, 생겨도 데이터를 잃지 않음 | 12 | 휴지통 폴더 안의 준비된 파일, 원문의 번역 그룹이 자기 id인 행 |
| 동시 요청에서만 차이 남 | 5 | 행 잠금, 동시 쓰기의 오류 매핑 |
| 코드가 잘못 불렀을 때만 차이 남 | 2 | 미리 준비한 초안 없이 item 폴더를 되살리는 호출 |

## 요구사항 중심 정리 (2026-10-30)

[계획](plan.md)대로 core를 기능의 요구사항 기준으로 봤다. core는 이미 빠르다. 로직 테스트 1,570개가 9초, DB 테스트 942개가 16초,
다른 사이트 설정 재실행 1,079개가 8초다. HTTP 라우트 테스트도 대부분 라우트가 맡을 일(권한, 상태 코드, 요청 형태)만 본다.
그래서 덜어낸 것은 적다.

- 휴지통: 3단계에서 과하게 더한 테스트 8개(데이터베이스 시계, 같은 밀리초의 시각 도장 4개, 없는 파일, 같은 파일 두 번, 커밋 뒤 알림 목록).
- `monti init`: 같은 것을 두 번 검사하던 것(두 번 돌리기, 미리보기)과 출력 문구의 세부 10개. 사용자 파일을 덮어쓰지 않기, 프로젝트 밖에 쓰지 않기는 남겼다.
- `monti doctor`: 출력 형식의 세부 6개. 비밀값을 출력하지 않는 검사는 남겼다.

다른 사이트 설정 재실행은 8초밖에 들지 않고 블로그 이름을 가정하는 테스트를 막는 장치라서 그대로 둔다.
