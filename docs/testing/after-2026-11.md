# 테스트 개편 뒤 측정, 2026년 11월

상태: 기록 (2026-11-02). [기준선](baseline-2026-10.md)과 같은 방법으로, 같은 컴퓨터에서 잰 결과다.

개편의 목표는 테스트 수를 줄이는 것이 아니었다([방향](plan.md)). 결함을 잡지 못하면서 비용만 드는 테스트(낭비)를 덜고, 테스트마다 이유와
자리를 두는 것(체계)이다. 그래서 이 문서는 그 두 물음으로 정리하고, 숫자는 근거로만 둔다.

## 어떻게 쟀나

- 기준선 코드(`overhaul`의 9053b8c2에 b31777ab를 더한 것)와 지금 코드(core 마무리 #401, 화면 테스트 시간 #400까지)를 **같은 컴퓨터에서 둘 다 다시** 쟀다. 기준선 문서의
  core 시간(89초)은 이 컴퓨터에서 기준선 코드를 다시 돌리니 26.5초였다. 측정 조건이 달랐던 것이라, 시간은 다시 잰 숫자끼리만 견준다.
- 커버리지는 기준선 문서의 숫자(88.5 / 76.3 / 84.4%)가 같은 명령으로 그대로 다시 나왔다. 측정이 같다는 확인이다.
- 약한 패턴과 블로그 이름은 지금의 스크립트를 두 코드에 똑같이 돌렸다.
- 변이 점수는 다시 재지 않았다. core 전체 점수는 2026-10-30에 소유자와 함께 버렸고, 대신 바뀐 줄만 재는 검사(`test:mutation:changed`)와
  지울 후보를 가리는 데 썼다(#381, #388).

## 낭비

### 다른 테스트가 이미 잡는 결함만 잡던 테스트

지운 테스트는 하나씩 [지운 테스트](deleted-tests.md)에 이유와 함께 있다. 겹침과 세부는 변이 테스트로, 그 테스트만 잡는 바꿈이 없을 때만 지웠다.

| | 기준선 | 지금 |
|---|---|---|
| 테스트 수(실행 기준) | 6,996 | 6,058 |

두 수 모두 같은 테스트를 다른 사이트 설정으로 한 번 더 도는 실행을 센다. 지금은 그것이 1,580개다(admin이 늘었다, 아래 "어느 사이트에서든").
core 빈틈을 채우며 더한 테스트도 들어 있다(아래 "빈틈").

테스트마다 필요한지 판정한 것은 admin, core, ui다. mdx, blocks, auth, syntax-shiki, syntax-directive, nextjs, seo, storage-s3의 약 710개는
요구사항 ID만 붙었고 판정은 거치지 않았다. ai는 #312에서 새로 쓴다.

### 시간

| | 기준선 | 지금 |
|---|---|---|
| 전체 한 번 | 122초 | 114~115초 (4번) |
| 그 가운데 테스트를 돌린 시간(파일 합) | 400초 | 330~351초 |
| core만 (L1, L2) | 26.5초 | 20.8초 |

- 전체 시간은 조금 줄었다. 테스트를 지운 만큼 줄지 않은 것은, 다른 사이트 실행과 빈틈 테스트가 늘었기 때문이다.
- 파일 시간 합의 절반 가까이를 화면 테스트(jsdom)가 쓴다. 890개(다른 사이트 실행 포함)가 150~172초다. 데이터베이스 테스트는 1,181개가 106~128초,
  평범한 로직은 3,821개가 36~41초, 브라우저 테스트는 166개가 23~26초다.
- 화면 테스트가 무거운 까닭을 재 보니, 파일마다 라이브러리를 다시 불러오는 시간과 이름으로 요소를 찾을 때 CSS를 맞춰 보는 시간이었다.
  #400에서 쓰지 않는 날짜 언어 데이터와 큰 묶음을 덜 불러오고, jsdom에서만 알림 스타일시트를 뺐다. 조용한 컴퓨터에서 화면 테스트만 번갈아
  잰 시간이 65~67초에서 56~60초로 줄었다. 파일마다 jsdom을 새로 만드는 비용(파일당 약 0.4초)은 격리를 끄지 않는 한 그대로다. 격리를 끄면
  모듈 mock이 먼저 불러온 모듈에 걸리지 않아 알림 검사가 아무것도 확인하지 않으므로 끄지 않았다.

### 순서와 반복

[`repeat-runs.mjs`](../../scripts/test-metrics/repeat-runs.mjs)로 CI처럼 10번, 순서를 섞어 10번, 워커 하나로 1번 돌렸다.

- CI처럼 10번, 워커 하나로 1번: 실패 없음. 10번 동안 실패가 없어도 한 번 실패할 확률은 많아야 26%다(95% 단측).
- 섞어서 10번: 테스트 둘이 한 번씩 실패했고, 둘 다 고쳤다.
  - core `write-hooks.int` WRITE-H2: 입력을 만들기 전에 글 수를 셌는데, 입력을 처음 만들 때 관계 대상이 생겨 먼저 돈 테스트가 하나를 더 셌다.
  - admin `code-block-features.browser` EDIT-C2: 부하가 걸리면 Playwright의 키보드가 프레임을 잃었다. 단축키를 페이지 안에서 보낸다.
- admin 마무리 중에 하나 더 찾았다: `entry-editor-shell` WRITE-P1이 혼자 돌면 실패했다(편집기가 한 프레임 늦게 포커스를 가져가 창을 닫았다).
- 기준선에서는 파일 안의 테스트 순서만 섞어도 3번 중 3번 실패했다.
- core 마무리 뒤 다시 섞어서 3번: 실패 없음. 설치 직후 첫 실행 한 번은 Vite가 실행 중에 새 의존성을 찾아 페이지를 다시 읽어서 브라우저 파일
  둘이 돌지 않았다. 캐시를 지우고 다시 돌려도 재현되지 않았다(#399에 적었다).

### 커버리지

테스트가 한 번이라도 실행한 코드의 비율이다.

| | 기준선 (줄 / 분기 / 함수) | 지금 |
|---|---|---|
| 전체 | 88.5 / 76.3 / 84.4% | 83.1 / 71.4 / 78.7% |
| ai를 빼고 | 89.8 / 77.7 / 86.0% | 89.1 / 76.8 / 84.9% |
| core에서 데이터를 쓰는 코드 | 94.9 / 81.5 / 95.7% | 97.1 / 86.8 / 97.4% |

- 떨어진 몫의 대부분(실행된 줄 1,649줄)은 ai다. 에이전트 개편(#312) 때 새로 쓰기로 하고 API 키 저장 테스트만 남겼다.
- ai를 빼면 1~2%p 떨어졌다. "작음"으로 지운 테스트가 실행하던 코드다(ui `list-head` 90 → 37%, admin `master-detail` 69 → 8% 등).
  망가져도 사용자가 알아채지 못하거나 다른 층이 막는다고 판정한 것이라, 커버리지를 지키려고 되살리지 않는다.
- 데이터를 잃을 수 있는 core 코드는 올라갔다. 아래 빈틈을 채운 결과다.

### 빈틈

core에서 데이터를 쓰는 14개 파일에 StrykerJS로 결함 3,601개를 넣었고, 어떤 테스트도 잡지 못한 것이 897개였다. 하나씩 보고, 데이터를 잃거나
사용자에게 틀린 것을 보이는 393개에만 테스트를 더했다(#401). 나머지는 결과가 같거나 사용자가 알 수 없는 차이다.

| 곳 | 못 잡던 결함 | 테스트로 막은 것 |
|---|---|---|
| 가져오기 | 276 | 185 |
| 복원 | 217 | 112 |
| 발행과 저장 | 189 | 66 |
| 스키마 변경 | 96 | 25 |
| 템플릿, 미디어, 폴더 | 119 | 12 |

그러면서 결함 넷을 찾아 고쳤다. 머리말이 틀린 줄을 말하지 않던 것(#401), 복원의 압축 해제 상한을 보는 테스트가 없던 것(#401), 가져오기
미리보기가 저장이 거부할 주소를 "가져옴"으로 보이던 것(#402), 쓰이던 태그를 버리면 그 글을 저장할 수 없던 것(#403).

테스트를 더한 약속 36개 가운데 29개에는 이미 테스트가 있었다. 그중 10개는 이제 두 층에서 본다(DATA-I1, I3, I4, I5, I7, R1, R5, R6, R7,
WRITE-W9). 있던 테스트를 넓히거나 옮겨야 했는지, 위 층 테스트가 이제 남는지는 요구사항 ID로 중복을 찾는 도구로 본다(#399).

## 남은 것

- **판정하지 않은 패키지**(#399): mdx, blocks 등 8개 패키지의 약 710개가 필요한지 판정한다. blocks·seo·ai의 약한 패턴 38개를 고친 커밋은
  판정 뒤 살아남은 테스트에만 쓰려고 `claude/blocks-weak-patterns` 브랜치에 두었다.
- **시각 회귀**(#334): 디자인 개편 뒤에 한다.
- **ai**: 에이전트 개편(#312) 때 규칙대로 새로 쓴다.
