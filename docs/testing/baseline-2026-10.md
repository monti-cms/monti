# 테스트 스위트 기준선, 2026년 10월

테스트 스위트 정비의 출발점이 되는 숫자다. 정비가 끝나면 같은 스크립트로 스위트를 다시 재고, 그 결과를 이 페이지와 견준다.
잰 코드는 `overhaul`의 9053b8c2에 휴지통 복원 수정(b31777ab)을 더한 것이다. 예전 휴지통 동작이 아래의 워커 하나 실행에서
실패했기 때문이다. 정비가 core부터 시작하므로 core는 따로 적는다.

## 숫자마다 재는 법

스크립트는 모두 `scripts/test-metrics/`에 있고, 각 스크립트 맨 위에 선택지 설명이 있다.

- **테스트와 시간**: Vitest JSON 리포터로 전체를 한 번 돌리고, 파일을 종류별로 나눈다(렌더링, 데이터베이스, CLI, 평범한 로직).
- **커버리지**: `packages/*/src`에 대해 `@vitest/coverage-v8`로 잰다. 테스트, 스토리, 테스트 도우미는 뺀다.
- **변이 점수**: `core-mutation-score.mjs`. `packages/core/stryker.score.config.mjs`를 `src` 폴더 하나씩 돌린다. M 시리즈 MacBook에서 2시간
  15분 걸렸다. 이 설정은 변이마다 처음 실패한 테스트에서 멈추고, 모듈 수준 코드의 변이(2,492개)를 뺀다.
  그래서 전체 설정보다 점수가 낮다(`plugin-storage.ts`: 여기서는 73%, `stryker.config.mjs`로는 83%). 이 설정의 점수는
  같은 설정의 점수와만 견준다.
- **약한 패턴**: `weak-patterns.mjs`. 2026-10-30에 세는 법을 고쳤고, 위 숫자는 고친 법으로 같은 코드(f3b3b69b)를 다시 센 것이다.
  처음 센 숫자는 1,785개(core 169개)였다. 그 안에는 문제가 아닌 쓰임이 섞여 있었다.
  - 한국어 문구: 화면에서 한국어 글자로 요소를 찾는 것(`getByRole(…, { name: "닫기" })`, `getByText("저장")`)만 센다. 글 제목 같은 한국어
    테스트 데이터는 세지 않는다.
  - 예외 목록(`EXEMPT`, 스크립트 안): 그 자리에서 맞는 쓰임을 이유와 함께 적는다. 렌더러가 내놓는 클래스와 속성(사이트 설정이 요청하고
    사이트 스타일이 읽는 출력), 테스트하는 코드가 쓴 파일을 읽는 것, 배포되는 `package.json`을 읽는 것 따위다. 예외는 패키지를 정비할 때
    쓰임을 하나씩 읽고 적는다. 지금은 core 것만 있다. 같은 목록을 정비 전후 코드에 똑같이 적용하므로 두 숫자를 견줄 수 있다.
- **참조 블로그 이름**: `site-names.mjs`.
- **불안정한 테스트와 순서**: `repeat-runs.mjs`. CI처럼 10번, `--shuffle`로 10번, `--one-worker`로 1번 돌린다. 파일 순서만 섞으면
  3번 중 3번 통과했고, 파일 안의 테스트 순서를 섞으면 3번 중 3번 실패했다.
- **리팩터링 커밋**: `test-churn.mjs --pr-commits`. squash된 커밋이 아니라 풀 리퀘스트 안의 커밋을 센다.

### 바로잡은 변이 점수

위 점수에는 가짜로 잡은 변이가 섞여 있었다. Stryker는 변이마다 그 코드를 실행하는 테스트만 골라 돌린다. 파일 안의 앞선 테스트가
남긴 것을 읽는 테스트는 혼자 돌면 변이가 없어도 실패하고, Stryker는 그 실패를 잡은 것으로 셌다.

정비 1단계(순서 의존 없애기) 뒤에 같은 설정으로 다시 재니 기준점에서 잡혔던 변이 886개가 살아남았다. 하나씩 까닭을 확인했다.

| 까닭 | 변이 | 확인한 법 |
|---|---|---|
| 기준점에서 잡은 테스트가 변이 없이 혼자 돌아도 실패한다 | 850 | 잡은 테스트 51개를 기준점 코드에서 하나씩 혼자 돌렸다 |
| 기준점 코드에 같은 변이를 넣고 그 테스트 파일을 다시 돌리면 잡히지 않는다 | 34 | 하나씩 손으로 넣어 돌렸다. 그 측정에서만 생긴 결과다 |
| 1단계가 검사를 약하게 만들었다 | 1 | 고쳤다(복원 안내 문구가 빈 글이어도 통과하던 검사) |
| 기준점에서 시간 초과였다 | 1 | 지금은 살아남는다. 정비 3단계에서 다룬다 |

34개 중 2개는 무작위 id의 순서에 따라 잡히기도 하고 안 잡히기도 한다(폴더를 부모보다 먼저 받는 복원, 컬렉션별 내보내기 정렬).
테스트가 운에 기대고 있다는 뜻이라 정비 3단계에서 고정된 데이터로 검사한다.

가짜 잡기 884개(850 + 34)를 빼면 core의 기준점은 **66.3% (23,036 / 34,747)**이다. 정비 뒤의 점수는 이 숫자와 견준다.

## 여기서 재지 않은 것

- 다른 패키지의 변이 점수: 각 패키지의 정비 전에 잰다.
- 시각 회귀: 나중에 따로 하는 단계다.
- 원본 보고서: 변이 하나하나의 보고서는 git 밖에 둔다(`**/reports/mutation`). 다른 숫자의 원본 실행 결과는 재시작으로
  잃었다. 이 페이지의 숫자가 남겨 둔 것이다.
