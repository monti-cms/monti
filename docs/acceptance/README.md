# 인수 조건 (AC)

AC는 테스트로 바로 바꿀 수 있을 만큼 구체적으로 쓴 "이런 상황이면 이렇게 되어야 한다"이다.
요구사항(`docs/refactor/`)이 무엇을 지킬지라면, AC는 무엇을 확인할지다. 소유자가 한 줄씩
승인하며, 테스트의 근거는 이 폴더뿐이다. 이 폴더는 소유자만 고치고 작업 에이전트는 읽기만 한다.

패키지마다 폴더를 따로 둔다(`docs/acceptance/core/` 등). 지금은 core만 있고, 다른 패키지는
각자의 리팩터링 때 폴더를 만든다.

## 형식

예: core의 `db/`

```
DB-3  마이그레이션이 중간에 실패한다
  전제  마이그레이션 3개가 순서대로 주어지고, 두 번째가 테이블을 만든 뒤 오류로 실패한다
  행동  core 마이그레이션을 실행한다
  결과  DB-3.1  두 번째 마이그레이션이 만든 테이블이 없다
        DB-3.2  `monti_migration_core`에 두 번째 마이그레이션이 기록되지 않는다
        DB-3.3  오류가 던져진다
```

- 번호는 영역 약어와 숫자다(`DB-3`). 결과 줄에는 `DB-3.1`처럼 AC 번호 뒤에 순번을 붙인다.
  한 번 쓴 번호는 다시 쓰지 않고, 없앤 번호는 비워 둔다.
- 전제는 행동 전에 참인 상황이다(0줄 이상). 행동은 정확히 하나다.
- 결과는 눈에 보이는 것으로 한 줄에 확인 하나씩 쓴다.

## 쓰는 법 (AC를 적는 사람)

1. 행동이 둘이면 AC를 나눈다. 결과 한 줄에 확인이 둘이면 줄을 나눈다.
   구현이 한 부분은 통과하고 다른 부분은 실패할 수 있으면 나눈다. 다만 객체 하나(`toMatchObject` 등)로 반환값이나 DB 행을 맞춰 보는 것은 확인 하나로 친다.
2. 코드에 나오는 이름(테이블, 열, 마이그레이션 이름)을 그대로 쓰고, 업계에서 통용되는 말을
   쓴다. 새 말을 만들지 않는다.
3. 테스트 준비용 데이터(픽스처)의 이름은 적지 않는다. 그건 테스트 코드가 정한다. 결과를
   가르는 값(테이블 목록, 경계 값)은 적는다.
4. "아무 일도 안 일어난다" 대신 눈에 보이는 결과(어느 테이블, 어느 행)를 쓴다.
5. **필요한 도메인 규칙에만 간결하게 쓴다.** 구현 실수나 엣지 케이스를 상상으로 미리 쪼개서 AC를 남발하지 않는다. 큰 리소스는 기능 묶음 단위로 나눠 승인하고 개발한다.

### 소유자 제출 전 체크리스트

초안은 대화 맥락에서 분리된 깨끗한 상태로 쓰고, 소유자에게 올리기 전에 다른 모델 1차 리뷰로 아래 5가지를 먼저 확인한다.

- **요약–AC 대조**: 상단 요약에 적은 규칙·오류 코드마다 대응 AC가 빠짐없이 있는가
- **중복 행동 금지**: 같은 행동을 확인 대상(테이블)만 나눠 2개 AC로 복제하지 않았는가
- **무관 규칙 합치기 금지**: 서로 무관한 규칙(예: 지정 `id` + 색인)을 한 AC에 욱여넣지 않았는가
- **현실성·스키마 대조**: 모순된 전제(`storage` 없음 + `media` 행 등)나 DB 제약·검증기와 어긋나는 전제가 없는가
- **가독성 기준선**: `db.md`·`engine.md`처럼 동사별로 묶여 각 AC가 1~2초 안에 읽히는가

## 테스트를 쓰는 법 (작업 에이전트)

- AC마다 테스트 하나를 쓴다. 제목은 영어이고 AC 번호로 시작한다.
- 각 `expect` 바로 위에 결과 번호를 주석으로 단다. 테스트 준비와 정리에는 `expect`를 쓰지
  않는다.

  ```ts
  it("DB-3 rolls back a migration that fails midway", async () => {
    // DB-3.3
    await expect(migrate(failing)).rejects.toThrow();
    // DB-3.1
    expect(await tableExists(...)).toBe(false);
    ...
  });
  ```

- 기대값은 AC 문장에서 가져온다.
- 테스트를 먼저 쓰고, 구현이 없어서(또는 동작이 달라서) `expect`가 틀려 실패하는 것을 확인한 뒤
  구현한다. 문법·import·준비 오류로 실패하면 테스트가 잘못된 것이다. 실패 메시지를 PM에게
  보고한다.
- 하지 않는 것: 번호 없는 테스트, 번호 없는 `expect`, 같은 번호의 테스트 둘, `skip`·`only`,
  테스트를 약하게 고쳐서 통과시키기.

## 끝났는지

자동 검사가 통과해야 끝이다: AC마다 테스트 하나, 결과 번호와 `expect` 일치, 건너뛴 테스트
없음, 문서에 없는 테스트 없음. 작업 에이전트의 "다 했다"는 말은 기준이 아니다.

단계 끝 Stryker 결과는 4분류로 정리해 보고한다:
1. **무의미 변이 무시**: 오류 메시지 문자열·동등 변이 등 관찰 결과가 바뀌지 않는 변이
2. **명세 밖 분기 삭제**: AC에 근거 없는 불필요한 방어 코드는 테스트를 늘리지 않고 코드에서 삭제
3. **기존 AC 보강**: 이미 승인된 규칙의 증인이 빠졌으면 해당 AC의 결과 줄을 보강
4. **새 규칙만 소유자 보고**: 새 오류 코드나 저장 동작이 필요할 때만 소유자 승인을 받아 AC에 추가

## 막혔거나 AC가 틀려 보일 때

AC를 고치거나 스스로 미루지 말고 PM에게 보고하고 기다린다. 미루기로 한 AC는 소유자가 제목
줄 끝에 `[보류: 사유]`를 적고, 자동 검사는 그 줄을 면제한다.
