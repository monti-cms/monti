# 인수 조건 (AC)

AC는 테스트로 바로 바꿀 수 있을 만큼 구체적으로 쓴 "이런 상황이면 이렇게 되어야 한다"이다.
요구사항(`docs/refactor/`)이 무엇을 지킬지라면, AC는 무엇을 확인할지다. 소유자가 한 줄씩
승인하며, 테스트의 근거는 이 폴더뿐이다. 이 폴더는 소유자만 고치고 작업 에이전트는 읽기만 한다.

패키지마다 폴더를 따로 둔다(`docs/acceptance/core/`, `docs/acceptance/cli/` 등). 새 패키지를 작업할 때 각자의 폴더를 만든다.

## 형식

각 문서는 **상단 요약 표**로 리소스 전체 동작을 한눈에 보여 주고, 아래 액션별 절 안에서 **`### 핵심 요구사항`**과 **`### 경계 · 방어 검증`**으로 나눠 AC를 배치한다.

- **핵심 요구사항 vs 경계 · 방어 검증 구분 기준**: *"이 제품을 기획서나 사용설명서로 설명할 때 입에 올리는 얘기인가?"*
  - **핵심 요구사항**: 정상 동작, 제품의 정체성을 이루는 핵심 도메인 정책(예: 휴지통 참조의 초안 보존·발행 차단)
  - **경계 · 방어 검증**: 잘못된 입력·빈 문자열·중복 충돌·없는 대상 거절, DB/스키마 경계값, 동시성 충돌·보안 계약, Stryker 보강 검증
- **접기(`<details>`) 마크다운**: 소유자가 평소에는 한 줄짜리 제목 목록으로 스펙 전체를 빠르게 훑고, 상세(`전제`·`행동`·`결과`)가 궁금한 항목만 펼쳐 볼 수 있게 `<details>`로 감싼다.

예: core의 `db/`

```markdown
<details>
<summary><strong><code>DB-MIG-3</code></strong> 마이그레이션이 중간에 실패하면 해당 마이그레이션을 롤백한다</summary>

- **전제**: 마이그레이션 3개가 배열에 순서대로 주어지고, 두 번째가 테이블을 만든 뒤 오류로 실패한다
- **행동**: `core` 마이그레이션을 실행한다
- **결과**:
  - `DB-MIG-3.1` 첫 번째 마이그레이션이 만든 테이블이 남아 있고 `migrations`에 첫 번째가 기록된다
  - `DB-MIG-3.2` 두 번째 마이그레이션이 만든 테이블이 없다
  - `DB-MIG-3.3` `migrations`에 두 번째와 세 번째 마이그레이션이 기록되지 않는다
  - `DB-MIG-3.4` 세 번째 마이그레이션은 실행되지 않는다
  - `DB-MIG-3.5` 오류가 던져진다

</details>
```

- 번호는 `영역-섹션-숫자` 2단 형식이다(`DB-MIG-3`, `ENT-PUB-1`). 섹션별로 카운터가 독립되어 각 섹션의 마지막 번호만 보고도 다음 번호를 알 수 있다. 결과 줄에는 `DB-MIG-3.1`처럼 AC 번호 뒤에 순번을 붙인다. 한 번 쓴 번호는 다시 쓰지 않고, 없앤 번호는 비워 둔다.
- 전제는 행동 전에 참인 상황이다(0줄 이상). 행동은 정확히 하나다(동시성 충돌을 검증하는 동시 호출 한 묶음은 행동 하나로 친다).
- 결과는 눈에 보이는 것으로 한 줄에 확인 하나씩 쓴다.

## 쓰는 법 (AC를 적는 사람)

1. 행동이 둘이면 AC를 나눈다. 결과 한 줄에 확인이 둘이면 줄을 나눈다.
   구현이 한 부분은 통과하고 다른 부분은 실패할 수 있으면 나눈다. 다만 객체 하나(`toMatchObject` 등)로 반환값이나 DB 행을 맞춰 보는 것은 확인 하나로 친다.
2. 코드에 나오는 이름(테이블, 열, 마이그레이션 이름)을 그대로 쓰고, 업계에서 통용되는 말을
   쓴다. 새 말을 만들지 않는다.
3. 테스트 준비용 데이터(픽스처)의 이름은 적지 않는다. 그건 테스트 코드가 정한다. 결과를
   가르는 값(테이블 목록, 경계 값)은 적는다.
4. "아무 일도 안 일어난다" 대신 눈에 보이는 결과(어느 테이블, 어느 행)를 쓴다.
5. **필요한 도메인 규칙에만 간결하게 쓴다.** 구현 실수나 엣지 케이스를 상상으로 미리 쪼개서 AC를 남발하지 않는다. 큰 리소스는 기능 묶음 단위로 나눠 승인하고 개발한다.

### 부분별 작성 톤

핵심 기준은 **"제목은 그 기능을 쓰는 사람이 겪는 일로 쓰고, 코드·DB 이름과 오류 코드는 `행동`과 `결과`에만 정확히 적는다"**다.

- **제목줄**: 소유자가 1~2초 만에 규칙을 이해하는 줄이다. 그 기능을 쓰는 사람(관리 화면을 거쳐 쓰는 편집자, 또는 코드를 쓰는 개발자)이 무엇을 할 수 있고 없는지를 쓴다. 시스템이 무엇을 검사하는지, 어떤 오류 코드·종료 코드를 내는지는 쓰지 않는다. 짧은 것보다 **바로 이해되는 것**이 우선이다. 한 제목에 규칙 하나만 적고, 내부 함수명·파라미터명(`from_id`, `trashed_at`)·오류 코드·압축 한자어("다중 관계", "조건부 하위 관계") 대신 쉬운 말로 풀어 쓴다. 다만 CLI 플래그(`--input`, `--dry-run`)나 사용자가 직접 다루는 파일명(`_snapshot.json`)처럼 사용자가 직접 보고 치는 표면 이름은 제목에 그대로 써서 맥락을 살린다. 편집자가 할 수 없게 되는 규칙은 왜 필요한지를 편집자 쪽 이유로 말할 수 있을 때만 쓴다.
  - Bad: `` `entries.replaceReferences`는 다중 관계에서 `into_id`가 이미 있으면 중복을 없애고 조건부 하위 관계도 함께 바꾼다 ``
  - Bad: `` `entries.publish`는 `trashed_at`이 설정된 글이면 `NOT_FOUND`로 거절한다 ``
  - Bad: `` 휴지통에 있는 글은 `NOT_FOUND`로 발행을 거절한다 ``
  - Good: `여러 개를 고르는 관계 필드에 바꿀 대상이 이미 들어 있으면 먼저 등장한 위치 하나만 남긴다`
  - Good: `휴지통에 있는 글은 발행할 수 없다` (오류 코드 `NOT_FOUND`는 `결과` 줄에 적는다)
- **전제**: 테스트에 필요한 최소 상황만 적는다. ① ② ③으로 여러 케이스를 한 전제에 몰아넣지 않고(케이스가 다르면 AC를 나눈다), 대상을 구분해야 하면 `A`, `B` 같은 알파벳 대신 `옛 글`, `새 글`처럼 역할이 드러나는 이름을 쓴다.
  - Bad: `같은 컬렉션에 활성 원문 글 두 개(from_id, into_id)가 있다. ① 작업본과 발행본이 다르고... ② many: true가 [into_id, from_id]이고... ③ 휴지통 글이 있다`
  - Good: `` 같은 컬렉션에 활성 원문 글 셋(옛 글, 다른 글, 새 글)이 있고, 다른 컬렉션의 글 하나가 `many: true` 관계 필드에 `[옛 글, 다른 글, 새 글]`을 가지고 있다 ``
- **행동**: 테스트가 실행할 정확한 호출 하나를 적는다. 정확한 액션 이름과 파라미터 이름(`from_id`, `into_id` 등)은 여기에 명시한다.
  - Bad: `참조 교체를 실행한다`
  - Good: `` 옛 글을 `from_id`, 새 글을 `into_id`로 넣어 `entries.replaceReferences`를 실행한다 ``
- **결과**: `expect` 하나와 1:1로 맞닿는 확인을 한 줄에 하나씩 적는다. 테이블명·열 이름·오류 코드(`BAD_REQUEST`, `CONFLICT`, `NOT_FOUND`)는 여기에 정확히 적고, "아무 일도 안 일어난다" 대신 어느 테이블의 어느 값이 그대로인지 적는다.
  - Bad: `오류가 나고 DB가 바뀌지 않는다`
  - Good: `` `NOT_FOUND` 오류를 던진다 `` / `` `<collection>_data` 테이블의 작업본 행이 원래 그대로이다 ``
- **상단 요약**: 액션별 요약 표(`액션 | 하는 일 | 주요 거절`)로 10초 안에 리소스 전체를 파악할 수 있게 정리한다.

### 소유자 제출 전 체크리스트

초안은 대화 맥락에서 분리된 깨끗한 상태로 쓰고, 소유자에게 올리기 전에 다른 모델 1차 리뷰로 아래 6가지를 먼저 확인한다.

- **요약–AC 대조**: 상단 요약에 적은 규칙·오류 코드마다 대응 AC가 빠짐없이 있는가
- **중복 행동 금지**: 같은 행동을 확인 대상(테이블)만 나눠 2개 AC로 복제하지 않았는가
- **무관 규칙 합치기 금지**: 서로 무관한 규칙(예: 지정 `id` + 색인)을 한 AC에 욱여넣지 않았는가
- **현실성·스키마 대조**: 모순된 전제(`storage` 없음 + `media` 행 등)나 DB 제약·검증기와 어긋나는 전제가 없는가
- **가독성 기준선**: `db.md`·`engine.md`처럼 동사·주제별로 묶여 각 AC가 1~2초 안에 읽히는가
- **동시성·보안 4질문** (모든 쓰기 액션과 공개 진입점):
  1. 같은 쓰기를 동시에 두 번 실행하면 무엇이 남는가? (DB `PK`·`UNIQUE` 포함)
  2. 짝 액션(삭제↔복원, 비밀번호 변경↔로그인, 부모 순환 이동 등)과 겹치면 무엇이 남는가?
  3. 반환값·로그·오류에 비밀값·내부 설정 객체·임의 경로가 섞여 나가지 않는가?
  4. 외부 입력의 크기·깊이·URL 스킴·스토리지 키 형식에 위험한 경계가 없는가?
  (걸리는 행동 계약만 락·암호화 구현 세부 없이 해당 리소스의 `경계 · 방어 검증`에 `<details>`로 추가한다)

## 테스트를 쓰는 법 (작업 에이전트)

- AC마다 테스트 하나를 쓴다. 제목은 AC 번호로 시작한다.
- 각 `expect` 바로 위에 결과 번호를 주석으로 단다. 테스트 준비와 정리에는 `expect`를 쓰지
  않는다.

  ```ts
  it("DB-MIG-3 마이그레이션이 중간에 실패하면 해당 마이그레이션을 롤백한다", async () => {
    // DB-MIG-3.5
    await expect(migrate(failing)).rejects.toThrow();
    // DB-MIG-3.2
    expect(await tableExists(...)).toBe(false);
    ...
  });
  ```

- 기대값은 AC 문장에서 가져온다.
- 테스트를 먼저 쓰고, 구현이 없어서(또는 동작이 달라서) `expect`가 틀려 실패하는 것을 확인한 뒤
  구현한다. 문법·import·준비 오류로 실패하면 테스트가 잘못된 것이다. 실패 메시지를 PM에게
  보고한다.
- 하지 않는 것: 번호 없는 테스트, 번호 없는 `expect`, 같은 번호의 테스트 둘, `skip`·`only`,
  테스트를 약하게 고쳐서 통과시키기.

## 끝났는지

자동 검사가 통과해야 끝이다: AC마다 테스트 하나, 결과 번호와 `expect` 일치, 건너뛴 테스트
없음, 문서에 없는 테스트 없음. 작업 에이전트의 "다 했다"는 말은 기준이 아니다.

단계 끝 Stryker 결과는 4분류로 정리해 보고한다:
1. **무의미 변이 무시**: 오류 메시지 문자열·동등 변이 등 관찰 결과가 바뀌지 않는 변이
2. **명세 밖 분기 삭제**: AC에 근거 없는 불필요한 방어 코드는 테스트를 늘리지 않고 코드에서 삭제. 단, 보안·동시성 방어 분기(길이·깊이 상한, 스킴·키 검증, 상수 시간 비교, 잠금 등)는 삭제하지 않고 4분류로 소유자에게 올린다
3. **기존 AC 보강**: 이미 승인된 규칙의 증인이 빠졌으면 해당 AC의 결과 줄을 보강
4. **새 규칙만 소유자 보고**: 새 오류 코드나 저장 동작이 필요할 때만 소유자 승인을 받아 AC에 추가

## 막혔거나 AC가 틀려 보일 때

AC를 고치거나 스스로 미루지 말고 PM에게 보고하고 기다린다. 미루기로 한 AC는 소유자가 제목
줄 끝에 `[보류: 사유]`를 적고, 자동 검사는 그 줄을 면제한다.
