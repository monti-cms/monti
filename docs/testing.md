# 테스트

> 2026-11-05에 다시 만들기를 시작하며 옛 테스트를 모두 지웠다. 새 테스트의 이름은 기능 문서의 끝 조건 번호로 시작한다
> ([build.md](design/features/build.md) 규칙 5). 옛 코드의 기록(요구사항 표, 변이 테스트, 기준 숫자)은 [`testing/`](testing/README.md) 아래에 남아 있고,
> 그것을 재던 스크립트(`scripts/test-metrics`, `pnpm check:tests`, `test:mutation`)는 옛 코드와 함께 지웠다. 2026-11-12에 그 절들을 이 문서에서 뺐다.

목표: 결함을 잡으면서, 돌리고 유지하는 비용이 적은 테스트. 테스트 수를 줄이는 것은 목표가 아니다. 테스트는 코드가 틀렸을 때 실패하고,
코드가 하는 일은 그대로인 채 코드만 바뀌었을 때 초록으로 남아야 제 몫을 한다.

## 테스트의 두 종류

- **동작**: 코드가 하는 일. 아래의 L1~L5 층이다. 이 페이지는 이것을 다룬다.
- **모양**: 관리자 화면이 어떻게 보이는지. Storybook 스토리, 시각 비교, 감사다(`packages/ui/visual`, `packages/ui` README 참고).
  동작 테스트는 모양을 검사하지 않는다. 클래스 이름, 페이지 위 요소의 순서, 폭을 보지 않는다.

## 층

층은 백엔드냐 프런트엔드냐가 아니라, 테스트가 동작을 검사하려면 무엇이 돌아야 하는지로 이름 붙인다. 프런트엔드 코드는 여러 층에 걸친다.

| 층 | 도는 것 | 파일 | 러너 | 예 |
|---|---|---|---|---|
| L1 로직 | 코드뿐 | `foo.test.ts`, JSX가 필요하면 `foo.test.tsx`(서버에서 HTML로 렌더하기 등) | Vitest, node | `membersToRestore`, `canTransition`, 슬러그 규칙, 스키마 diff |
| L2 통합 | Postgres, 파일 시스템, 자식 프로세스 | `foo.int.test.ts` | Vitest, node, 테스트 데이터베이스 | 스토어가 휴지통에 든 묶음을 복원하기, 마이그레이션, `monti init` |
| L3 부품 | `@monti-cms/ui`의 부품 하나 | `foo.browser.test.tsx` | Vitest 브라우저 모드 | 메뉴의 키보드, 끌기 |
| L4 화면 | PGlite 위의 사이트와 관리자 화면 전체, 스토리 장면 위의 실제 입력 | `foo.screen.test.tsx` | Vitest 브라우저 모드 (`pnpm test:browser`) | 흐름의 단계, `testing/scenes.ts`의 장면 |
| L5 흐름 | 시험용 서버(`testing/e2e`), 진짜 Postgres, HTTP, 디스크, 브라우저 | `testing/e2e/<flow>.e2e.ts` | Playwright (`pnpm test:e2e`) | 파일을 올리고, 글에 넣고, 발행하고, 사이트에서 보기 |

**동작 하나에 층 하나.** 동작은 그 결함을 잡을 수 있는 가장 낮은 층에서 한 번만 테스트한다. 함수인 규칙은 L1에서 테스트하고,
데이터베이스, HTTP 라우트, 화면을 거쳐 다시 테스트하지 않는다. 높은 층은 층들이 이어지는지(라우트가 서비스를 부르고, 화면이 요청을 보낸다)를
검사하고, 모든 경우를 다시 검사하지 않는다. L5는 조각을 다 합쳐야만 깨지는 이음매만 본다(HTTP와 쿠키, 디스크의 파일, 브라우저가 그림을 해독하는지, 사이트에 그린 결과).
흐름마다 지키는 이음매와 끊어 보는 법은 [흐름 테스트가 지키는 이음매](testing/flows.md)에 있다. L5는 PR마다 돌고 재시도하지 않는다. 실패하면 그 테스트나 앱을 고친다.
`pnpm test:e2e`는 시험용 데이터베이스의 스키마 `monti_e2e`를 매번 비우고 표를 만든 뒤 흐름을 돌린다. 사이트에 붙이는 길(T13)이 생기기 전이라 `testing/e2e`의 작은 서버가 관리자 API와 관리자 화면을 띄운다.

**jsdom이냐 실제 브라우저냐.** jsdom은 아무것도 그리지 않는다. 모든 상자는 0 × 0이고, 캐럿에는 위치가 없으며, 포커스와 타이머는 브라우저처럼 움직이지 않는다.
동작이 그중 어느 것에도 기대지 않는 컴포넌트(메뉴의 항목, 폼의 검증)에는 괜찮다. 위치, 크기, 포커스 이동, 편집기가 필요한 테스트는
`*.browser.test.tsx`로 간다. jsdom을 넘기려고 크기를 지어내거나 브라우저 API를 스텁하는 테스트도 그쪽에 속한다.
L3, L4의 브라우저 테스트는 Vitest 브라우저 모드로 Chromium에서 돈다(Playwright, 1440 × 900, UTC). 처음 한 번 `pnpm exec playwright install chromium`으로
브라우저를 받고, admin은 `pnpm --filter @monti-cms/admin test:browser`, ui는 `pnpm --filter @monti-cms/ui test:browser`로 돌린다. 브라우저에서는 Node 모듈을 읽을 수 없으므로, 브라우저 테스트가 쓰는
도우미는 서버 코드를 끌어오지 않는다(`@monti-cms/core/testing` 대신 그 모듈을 직접 가져온다). 서버 코드가 꼭 필요한 검사(가짜 API의 경로가
코어에 있는지)는 Node에서 도는 브라우저 명령(`commands`)으로 테스트가 끝난 뒤 한다. 단축키는 `userEvent.keyboard`(`vitest/browser`)로
실제 키를 누르고, `Mod`는 `ControlOrMeta`로 적는다. 편집기의 `Mod`는 Mac에서 ⌘, 다른 곳에서 Ctrl이다.

## 프런트엔드

- **훅이 아니라 판단을 뽑아낸다.** 컴포넌트가 경우가 많은 것을 정할 때(선택한 행에 어떤 일괄 동작을 허락하는지, 슬래시 메뉴가 무엇을 보이는지),
  그 판단은 입력을 받는 평범한 함수가 되고 L1에서 테스트한다. 경우가 많거나, 판단을 여러 곳에서 쓰거나, 비동기 상태 기계일 때만
  뽑아낸다(`entry-editor-store`처럼 React 없이 도는 평범한 객체). 나머지는 모두 컴포넌트에 남기고 거기서 테스트한다. 그러면 컴포넌트가 그것을
  어떻게 쓰는지도 함께 테스트된다.
- **훅 테스트는 없다.** 훅은 따로 테스트하지 않는다. 그 훅을 쓰는 컴포넌트를 거쳐 테스트하거나, 그 판단을 함수로 뽑아낸다.
- **Storybook은 모양을 위한 것이다.** 스토리는 카탈로그, 시각 비교, 접근성 검사다. 스토리의 `play`는 볼 상태(열린 메뉴)를 만들고, 그 상태에
  닿았는지만 기다린다. 동작의 결과(저장됐는지, 순서가 바뀌었는지)는 L4 화면 테스트가 그 스토리를 띄워 놓고(`composeStories`) 실제 입력으로 확인한다.
  전에 쓴 스토리에는 결과까지 보는 `play`가 남아 있다. 그 스토리를 고칠 때 테스트로 옮긴다.

## 화면을 확인하는 장치

화면의 결함은 대부분 시키지 않은 길에 있었다: 마우스가 가는 도중에 숨는 버튼, 문장 중간에서는 안 열리는 메뉴, 하나 더하면 넘치는 표. 그래서 써 볼 길을
먼저 적어 두고 장치가 빠진 것을 막는다. 규칙을 글로만 두면 건너뛰게 된다.

| 장치 | 하는 일 | 왜 |
|---|---|---|
| [`testing/scenes.ts`](../testing/scenes.ts) | 부품 종류마다 써 볼 장면의 목록. 빠져나간 결함은 장면이 된다 | 써 볼 길을 그때그때 떠올리면 같은 길을 또 빠뜨린다 |
| `pnpm check:scenes` | 화면 코드가 쓴 부품 종류의 장면 테스트가 그 폴더에 있는지(`it("[reach] …")`), 부품 자체의 장면이 ui에 있는지, `it.todo` · `.only` · 진행 기록 번호 없는 `skip`이 없는지 | 장면을 빼거나 건너뛴 채로 push하지 못하게 한다. `.husky/pre-push`, CI, Claude hook(`git push`와 `gh pr create` 앞)에서 돈다 |
| `testing/input.ts` | 실제 입력: `pointerPath`(손이 가는 길), `dragPath`와 `dropDrag`(끌기의 중간과 놓기), `typeKorean`(조합 중인 한글), `pickWords` · `caretAfter`(글자 고르기와 커서 놓기) | 이벤트를 직접 쏘면 사람이 지나는 틈을 지나지 않는다. 가짜 클릭은 본문 이미지를 고르지 못했다 |
| `packages/admin/test/scene.ts`의 `scene` | 스토리에 없는 상태를 테스트가 만들고, 그 사이트의 기능을 테스트가 읽는다 | 검사만 하려고 스토리를 늘리지 않는다. 화면에 보인 것과 저장된 것을 함께 본다 |
| 스킬 `screen-build` | 화면 승인(목업) → 장면을 `it.todo`로 → 만들기 → 소유자 → 코드 리뷰 → 디자인 리뷰 → 브라우저 확인 | 글로 승인한 문서는 만든 뒤에 다시 정하게 된다 |
| `pnpm check:review`와 병합 hook | 디자인 리뷰가 읽은 화면만 병합한다 | 읽지 않고 들어간 화면에서 결함이 나왔다(#461) |

장치가 못 보는 것은 사람이 본다. `check:scenes`는 테스트 이름만 읽으므로 테스트가 장면이 말한 일을 하는지는 코드 리뷰가 읽는다. 새 테스트는 그것이 지키는
바꿈을 뺀 코드에서 한 번 실패하는지 돌려 본다. 없는지를 보는 검사는 있는 것을 보는 검사 옆에 둔다(안 그러면 화면이 뜨기 전에 통과한다).

## 테스트 쓰기

모든 테스트는 세 질문에 답한다. 하나라도 답이 없으면 그 테스트는 쓰지 않는다.

1. **무엇을 약속하는가?** 누군가 기대는 동작이다. 공개 함수, HTTP 라우트, CLI 명령, 관리자가 화면에서 할 수 있는 일.
2. **어느 층인가?** 그것을 잡을 수 있는 가장 낮은 층.
3. **코드가 어떻게 틀려야 실패하는가?** 결함을 이름으로 댄다. 어떤 값에도 통과하는 테스트(`toBeDefined`, `toBeTruthy`)는
   아무것에도 답하지 않는다.

### 무엇이 테스트의 이유인가

기능 문서의 끝 조건이다. 끝 조건을 지키는 테스트는 제목 앞에 그 번호를 단다(`it("11-1 …")`). `pnpm check:operations`가 번호가 어느 문서에 있는지 본다.
화면을 써 보는 길은 장면이고, 제목에 장면 이름을 단다(`it("[reach] …")`). 화면 테스트는 한국어 화면에서 돌고, 화면에 보이는 문구로 찾는다.

### 테스트는 저마다 홀로 선다

테스트는 필요한 상태를 스스로 만들고, 다음 테스트에 아무것도 남기지 않는다. 혼자 돌려도(`-t`), 어떤 순서로 돌려도(`--sequence.shuffle`) 통과한다.
한 시나리오를 단계로 돌리는 파일(만들기, 바꾸기, 적용)은 단계가 있는 테스트 하나다. 서로의 상태를 읽는 여러 테스트가 아니다.

### 기다리기

조건을 기다리거나(`findBy…`, `waitFor`, `expect.poll`) 가짜 시계를 움직인다(`vi.useFakeTimers`). 정해진 시간을 기다리지 않는다.

## 금지

| 패턴 | 까닭 | 대신 |
|---|---|---|
| 결과나 오류에 `toBeDefined()` | 어떤 값, 어떤 오류에도 통과한다 | 값이나 오류 코드를 검사한다 |
| 요소나 값에 `toBeTruthy()` | 있기만 하면 무엇이든 통과한다 | 무엇이어야 하는지 검사한다 |
| 정해진 시간 재우기(`setTimeout`, `sleep(n)`) | 느리고, 느린 기계에서는 여전히 불안정하다 | 조건을 기다리거나, 가짜 시계 |
| 건너뛰려고 테스트 안에서 `return` | 돌지 않은 테스트를 통과로 알린다 | `it.skipIf(…)`, 또는 필요한 것을 만든다 |
| 동작 테스트의 클래스 이름, data 속성, DOM 순서 | 컴포넌트가 어떻게 만들어지고 보이는지다 | 역할과 이름. 모양은 시각 테스트로 |
| `querySelector`, 테스트 id | 테스트를 마크업에 묶는다 | 역할과 이름(`getByRole`) |
| 패키지 자기 모듈의 mock | mock을 테스트하고, 내부를 조금만 옮겨도 깨진다 | 모듈을 그대로 쓴다. 가장자리(네트워크, 시계, 모델)만 mock한다 |
| 위치로 읽는 mock 호출 인자(`mock.calls[0][1]`) | 인자가 하나 더해지면 깨진다 | 중요한 것만 담은 `toHaveBeenCalledWith` |
| 소스 파일을 글자로 읽어 검사하기 | 서식이 바뀌면 깨지고, 동작에 대해 아무것도 말하지 않는다 | 코드가 하는 일을 테스트한다. 타입 검사는 `tsc`의 몫이고, 무엇을 가져와도 되는지 같은 코드 규칙은 lint의 몫이다(`biome.json`의 `noRestrictedImports`, `biome-plugins/`) |

이 표는 리뷰가 본다. 세는 스크립트는 지금 없다.

## 파일

- 테스트는 테스트하는 것 옆에 두고 그것의 이름을 따른다(`list-screen.tsx` → `list.screen.test.tsx`). 테스트를 더한 작업의 이름은 따르지 않는다.
- 접미사가 층을 말한다. `.test.ts(x)`(L1), `.int.test.ts`(L2), `.browser.test.tsx`(L3), `.screen.test.tsx`(L4), `.e2e.ts`(L5). 층마다 자기 Vitest 프로젝트라 한 층만 따로 돌릴 수 있다.
- 여러 테스트가 쓰는 도우미는 패키지의 `test` 폴더와 저장소의 `testing` 폴더에 둔다.

## 사용성 확인

2026-11-09, 소유자: 문서 09에서 해 본 결과로 정했다.

- **GPT-6.1 Terra 시험은 필수 절차가 아니다.** 큰 화면이 새로 생겨 소유자가 부탁할 때만 돌린다. 드라이버(`testing/usability`)는 그때를 위해 남긴다. 4회 시험에서 문구와 상태 변화의 헷갈림은 찾았지만, 가장 큰 결함은 시키지 않은 행동에 있어 찾지 못했다.
- **겹침 자동 검사는 넣지 않는다.** 호버 때 나오는 버튼까지 도는 검사를 임시로 만들어 보니 일부러 만든 겹침은 잡았지만, 실제 화면에서는 쓰는 데 지장 없는 툴팁 하나만 나왔다. 같은 겹침이 되풀이되면 그때 다시 본다.
- **결함이 나오면 그 흐름을 L4나 L5 테스트로 더한다.** 파일 여러 개 놓기, 붙인 뒤 이어 쓰기가 그렇게 들어갔다.
- **보기에 어색한 것과 문구는 쓰면서 고친다.**
