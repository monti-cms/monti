# 미디어 사용성 점검 — feat/media-09

2026-11-09, 제공된 Chromium과 테스트 데이터로 확인. 화면을 직접 볼 수 있었다. 명령은 별도 표시가 없으면 `node testing/usability/do.ts` 뒤에 적은 것이다. 좌표는 당시 창 크기에 따른다. 데이터는 테스트 과정에서 변경했다.

## 발견한 문제

### A 막힘 — U5: 목록 항목에 붙여 넣은 그림이 목록 밖에 들어감

- 재현: `open /`에서 게시글 “아침의 책상”을 열고, 그림이 있는 본문을 스크롤한 뒤 `click 125 610`, `key End`, `clip testing/usability/files/붙여넣기.png`, `key Meta+V`. 당시 창은 1024×768이었다. 목록 항목 “덜어낸 것”을 눌러 그 끝에 붙여 넣었다.
- 화면: [064.png](../../.usability/feat-media-09/064.png), 삽입된 그림을 스크롤해 본 [095.png](../../.usability/feat-media-09/095.png).
- 기대: 목록 항목 안의 커서 자리에 그림이 들어간다. 기능 09의 원칙 4와 흐름 6의 05단계는 붙여 넣은 이미지를 커서 자리에 넣도록 한다.
- 실제: 목록은 “덜어낸 것” 한 항목으로 끝나고, 새 그림은 목록 다음의 독립된 블록으로 나타났다. 접근성 트리에서도 그림의 캡션이 `list` 바깥에 있었다. 원한 위치에 넣는 작업을 완료하지 못했다.

### A 막힘 — U11: 번역에서 원문 대표 이미지가 비어 보이고 대체 텍스트만 쓸 수 없음

- 재현: “아침의 책상” 한국어에서 대표 이미지 `표지-봄.jpg`, 대체 텍스트 `봄 표지`를 지정하고 저장한다. `+ 언어`에서 English를 만든 뒤 `속성`을 연다. 이후 게시글 목록에 나갔다가 다시 열고 English와 속성을 다시 열어도 같다. 이때 한국어 속성에서 파일과 대체 텍스트가 저장되어 있는 것을 다시 확인했다.
- 화면: 한국어 [059.png](../../.usability/feat-media-09/059.png), English [062.png](../../.usability/feat-media-09/062.png). 다른 파일을 고른 뒤 [106.png](../../.usability/feat-media-09/106.png), 빼기 후 [107.png](../../.usability/feat-media-09/107.png).
- 기대: 기능 09의 “대체 텍스트” 절은 번역의 빈 미디어 값이 원문의 파일과 대체 텍스트를 따르고, 번역에서 대체 텍스트만 쓸 수 있다고 정한다. 현재 원문 값과 번역값을 구별할 수 있어야 한다.
- 실제: English의 대표 이미지는 “비어 있음”으로 보였고 대체 텍스트 입력칸도 없었다. 파일을 직접 고른 뒤에야 대체 텍스트 칸이 나타났다. 다른 파일을 골랐다가 빼자 다시 “비어 있음”이 되었고 원문을 따른다는 표시는 보이지 않았다. 화면만으로 실제 사이트 출력이 어떤 값을 따르는지는 확인하지 않았다. 원본 이미지를 유지하면서 대체 텍스트만 번역하는 첫 단계를 완료하지 못했다.

### B 헷갈림 — U2: HEIC가 이미지인데 “이미지만”이라는 이유로 거절됨

- 재현: 미디어 화면에서 `dropfile testing/usability/files/아이폰-사진.heic testing/usability/files/설치.exe testing/usability/files/아주-큰-사진.png 700 400`, `wait 700`, `shot`.
- 화면: [007.png](../../.usability/feat-media-09/007.png).
- 기대: 기능 09 원칙 4는 실패 이유를 제자리에 남기고, 받는 종류 절은 HEIC를 받지 않는다고 명시한다. 아이폰 사진을 올린 사람이 그 사진 형식을 바꿔야 한다는 것을 알아야 한다.
- 실제: HEIC와 exe 모두 “이미지 · PDF · ZIP · 텍스트만”이라고 표시됐다. HEIC는 사진인데 이미지가 허용된다고만 보여 왜 거절됐는지와 다음에 무엇을 해야 할지 분명하지 않았다. 큰 사진은 `18.8 MB · 10 MB까지`와 `줄여서 다시`가 보였다.

### B 헷갈림 — U7: 선택한 파일에서 Delete 키가 반응하지 않음

- 재현: `새사진` 폴더에서 사용 안 함 타일의 체크박스를 `click 307 212`로 선택하고 `key Delete`. 같은 조작을 다른 사용 안 함 파일에서도 반복했다. 체크박스에 포커스가 있는 상태였다.
- 화면: [098.png](../../.usability/feat-media-09/098.png), 반복 확인 [102.png](../../.usability/feat-media-09/102.png).
- 기대: `docs/design/admin/screens/media.md`의 파일 오른쪽 클릭 항목은 휴지통으로 옮기는 경로에 Del 키를 명시한다.
- 실제: 선택 표시와 파일이 그대로 남았고 알림도 나타나지 않았다. 일괄 막대의 `휴지통으로`를 클릭하면 삭제할 수 있었다.

### B 헷갈림 — U10: 업로드 중 이탈 경고가 대기 파일을 변경사항이라고 부름

- 재현: 1024×768에서 `가격표-2026.pdf` 복사본 200개를 `.usability/feat-media-09/bulk/`에 만들고 `dropfile .usability/feat-media-09/bulk/*.pdf 450 450`. 업로드와 대기가 보일 때 `click 70 80`으로 게시글에 가려고 한다.
- 화면: [056.png](../../.usability/feat-media-09/056.png), 경고 [057.png](../../.usability/feat-media-09/057.png).
- 기대: 기능 09 원칙 4와 흐름 6의 03단계처럼 파일이 올라가거나 대기하는 상황을 알 수 있고, 나갈 때 무엇이 중단되는지 이해할 수 있다.
- 실제: “저장하지 않은 바뀐 곳이 있어요”, “나가면 바뀐 곳 106개가 사라져요”, “저장하지 않고 나가기 / 계속 고치기”라고만 나왔다. 파일 업로드를 하고 있었으므로 이 숫자가 무엇이고 업로드가 어떻게 되는지 표현만으로는 분명하지 않았다. `Escape`로 돌아간 뒤 업로드가 이어져 총 203개가 됐다. 실제로 나가기를 확정했을 때의 결과는 확인하지 않았다.
