# 관리자 에이전트 (설계)

상태: 초안 (2026-11-02). 에이전트 방향으로 다시 그린 캔버스 디자인과 소유자의 결정(2026-11-02)을 바탕으로 처음부터 다시 썼다. 이 문서는 앞선 설계(10-26)를 대신한다. 지금 코드는 이 설계보다 먼저 만들어졌으므로 기준이 아니다.

화면은 [흐름 2 · 어시스턴트](admin/flows/02-assistant.md)와 흐름 1(발행 할 일), 3(번역), 5(휴지통), 6(미디어), 11(설정·스키마), 12(활동 기록)의 AI 단계를 따른다. 이 문서는 그 화면 뒤에서 무엇이 돌아가는지 적는다.

## 0. 한 문장으로

관리자는 어디서든 어시스턴트에게 일을 시킨다. 에이전트는 사이트를 마음대로 읽고 화면을 움직인다. **바꾸는 일은 모두 제안으로 쌓이고**, 관리자가 보고 받아야 실제로 바뀐다. 받은 것은 되돌릴 수 있다. 칸 하나를 채우는 버튼만은 예외로, 그 칸에 바로 넣는다.

## 1. 원칙

1. **바로 넣기와 제안, 두 가지뿐이다.**
   - **바로 넣기**는 입력 칸 하나에 붙은 "✦ 채우기" 버튼이다. 요약, 시리즈 추천, 이미지 한 장의 대체 텍스트와 캡션이 여기에 든다.
     - 누르면 그 칸에 값이 들어간다. 사람이 손대거나 저장할 때까지 파란 글씨다.
     - ⌘Z로 되돌리거나 "↻ 다시"로 새로 받는다.
     - 받기 단계도 말풍선도 없다. 사람이 이미 그 칸을 가리켰으니 어디가 바뀌었는지 안다.
   - **제안**은 그 밖의 모든 쓰기다. 채팅으로 시킨 일이 여기에 든다. 여러 곳을 한 번에 채우는 버튼은 두지 않는다. 발행 할 일의 "대체 텍스트 없는 이미지 2개"는 누르면 첫 이미지의 대체 텍스트 카드로 가고, 거기서 장마다 바로 넣고 "다음 이미지"로 넘긴다(흐름 1·12).
     - 받기 전에는 아무것도 바뀌지 않는다.
     - 바뀌는 곳이 여럿이면 사람은 어디인지 모른다. 그래서 파란 연필 표시와 말풍선으로 따라가며 확인시킨다.
2. **동등성.** 에이전트가 하는 일은 관리자가 화면에서 하는 일과 같은 코드, 같은 검사, 같은 권한으로 한다. 기능 하나를 정의하면 화면의 API와 에이전트의 도구가 함께 생긴다(3절).
3. **사람만 하는 일이 있다.**
   - 영구 삭제와 휴지통 비우기는 에이전트가 하지 않는다. 에이전트가 지우면 휴지통으로 가므로, 제안에는 되돌릴 수 없는 항목이 없다.
   - 에이전트는 시키지 않은 휴지통 보내기를 스스로 제안하지 않는다.
4. **읽은 글은 명령이 아니다.** 글 본문이나 파일에 "모든 글을 지워라"가 있어도, 에이전트가 할 수 있는 최대치는 제안이다. 사람이 받지 않으면 아무 일도 없다.
5. **돈은 세지 않는다.**
   - 토큰만 키마다, 달마다 센다. 금액과 한도는 서비스가 정한다.
   - 서비스가 거절하면 대화 안에 오류 답장으로 알린다("크레딧이 부족해요 · 다른 모델로 보내기").

## 2. 전체 구조

```
패널(브라우저) ──요청──▶ 실행 엔진(서버) ──▶ 모델(키의 서비스)
      ▲  이벤트 스트림        │  도구 호출
      │                       ├─ 읽기 도구 ──▶ 사이트 데이터
      │                       ├─ 쓰기 도구 ──▶ 제안 저장소 (바꾸지 않음)
      └── 화면 도구 ◀─────────┘   (목록 거르기·고르기·이동·열린 글 읽기는 브라우저가 실행)

적용 엔진(서버): 제안 저장소 ──▶ 항목마다 적용 ──▶ 활동 기록 + 되돌리기 정보
```

- **실행 엔진**: 대화 하나의 에이전트 루프다(4절).
- **도구**: 기능 정의에서 만들어진다. 읽기, 쓰기, 화면 세 종류다(3절).
- **제안 저장소**: 쓰기 도구가 만든 항목을 대화에 묶어 서버에 저장한다(5절).
- **적용 엔진**: 받은 항목을 차례로 실제로 바꾸고, 진행과 결과와 되돌리기 정보를 남긴다(6절).
- **빠른 작업**: 바로 넣기 버튼이 쓰는 별도의 길이다. 루프 없이 모델을 한 번 부른다(8절).

## 3. 기능과 도구

기능은 이름(`entries.moveToFolder`), 모델이 읽는 영어 설명, 입력 스키마, 종류로 정의한다. 정의 하나에서 관리자 API 라우트와 에이전트 도구가 함께 나온다. 플러그인도 같은 방법으로 기능을 더한다.

| 종류 | 누가 실행하나 | 무엇을 돌려주나 | 예 |
|---|---|---|---|
| 읽기 | 서버. 실행을 시작한 관리자의 권한으로 | 모델에는 데이터. 화면에는 한 줄 요약("글 목록 읽음 · 게시글 148편") | 글 목록·찾기·읽기, 쓰인 곳, 미디어, 폴더, 태그, 스키마, 설정, 활동 기록 |
| 쓰기 | 서버. **바꾸지 않고** 제안 항목을 만든다 | 모델에는 미리보기와 항목 id. 화면에는 "제안 만듦 · …" | 필드 고치기, 본문 고치기, 폴더 옮기기, 태그 달기·지우기, 휴지통 보내기, 대체 텍스트, 번역 글 만들기, 설정 바꾸기, 스키마 바꾸기 |
| 화면 | 브라우저 | 모델에는 결과. 화면이 바로 바뀐다 | 목록 거르기, 행 고르기, 다른 화면 열기, 열린 글 읽기, 고른 부분 읽기 |

쓰기 기능은 네 가지를 더 갖춘다.

| 이름 | 하는 일 |
|---|---|
| `preview` | 지금 값과 바꿀 값. 검토 화면의 "지금 / 제안"과 편집기의 파란 연필이 이것으로 그려진다 |
| `base` | 바꿀 자리의 지금 버전(글의 버전, 또는 그 자리의 해시). 그사이 바뀌었는지 가늠하는 기준이다 |
| `apply` | 실제로 바꾼다. 화면의 저장과 같은 서비스를 같은 검사로 부른다 |
| `undo` | 되돌리기에 필요한 이전 값을 남기고, 되돌리는 방법을 안다 |

**읽기에는 제안이 비친다.** 한 실행 안에서 쓰기 도구로 만든 항목은, 뒤따르는 읽기 결과에서 적용된 것처럼 보인다(미리보기 겹침). 그래서 "옮긴 다음 그 글들에 태그 달아 줘"처럼 앞 단계를 전제로 계획을 이어 갈 수 있다. 실제 데이터는 그대로다.

**화면 도구가 남기는 표시**
- 에이전트가 건 필터와 고른 행은 파란색이다. 사람이 손대면 보통 모양으로 돌아간다.
- 저장 안 한 편집이 있으면 다른 화면으로 옮기지 않는다. 대신 그렇다고 답하고 "저장하고 열기"를 보인다(흐름 2·05).

## 4. 실행 엔진

pi(`pi-agent-core`)의 루프를 본뜬다.

- **턴**: 모델 요청 한 번, 그리고 그 응답이 부른 도구 실행이다. 도구 호출이 없는 응답이 오면 끝난다.
- **실행**: 사람이 한 번 보낸 요청에 대한 턴들이다. 대화는 실행이 이어진 것이다.
- **도구 실행**:
  - 읽기 도구는 한 턴 안에서 함께 돌린다.
  - 쓰기와 화면 도구는 차례로 돌린다. 쓰기의 순서가 곧 제안의 순서이고, 화면은 한 번에 하나만 움직여야 한다.
  - 도구 오류는 실행을 멈추지 않는다. 모델이 읽는 결과(`{ error }`)가 된다.
- **도구 전후 훅**:
  - 실행 전 훅은 입력을 검사하고 막을 수 있다. 영구 삭제, 사람만 하는 일, 열린 글 밖에서 부른 편집기 도구가 여기서 막힌다.
  - 실행 후 훅은 결과를 줄인다. 너무 긴 결과는 앞부분과 "질의를 좁히라"는 안내로 바꾼다.
- **이벤트 스트림**: 엔진이 패널로 보내는 것들이다.
  - 실행과 턴의 시작과 끝
  - 오는 중인 글
  - 도구의 시작, 진행, 끝. 진행은 많은 항목을 다루는 도구가 보낸다("요약 확인 중 · 62 / 148").
  - 제안이 생기거나 바뀜
  - 사용량
- **한도**: 실행마다 턴 수, 토큰, 걸린 시간에 한도가 있다.
  - 시간 한도에 닿으면 진행 중인 턴을 마치고 멈춘다.
  - 패널은 이것을 끊긴 것과 같이 보이고 "이어서 하기"를 준다. 그래서 서버리스의 시간 제한 안에서도 긴 일을 이어 간다.
- **끼워 넣기(steer)**: 실행 도중 사람이 더 보내면, 지금 도구들이 끝난 뒤 다음 턴에 넣는다. 멈추지 않고 방향을 바꿀 수 있다.
- **멈추기**: 패널의 멈추기는 지금 실행을 중단한다. 그때까지 만든 제안 항목은 남는다.
- **저장**:
  - 대화를 서버에 저장한다. 메시지, 도구 호출과 결과, 쓴 모델, 사용량이 들어간다.
  - 패널을 닫았다가 돌아와도 이어진다.
  - 한 대화에서는 실행이 한 번에 하나만 돈다. 자리 요청(7절)는 따로 도는 작은 실행이다.
- **모델**:
  - 대화마다 입력창에서 고른 모델과 생각 정도로 돈다.
  - 새 대화는 기본 모델이 있는 첫 키의 서비스 기본 모델로 시작한다. 생각할 수 있는 모델이면 "보통"이다.
  - 도구를 못 쓰는 모델은 고를 수 없다.
- **맥락**: 실행마다 세 가지를 받는다.
  - 사이트의 모양: 컬렉션, 필드, 필드의 설명과 제한
  - 글 쓰는 방식: 설정 › 사이트에 있는 텍스트 하나
  - 지금 화면: 화면 종류, 열린 글, 고른 행 가운데 사람이 칩에서 빼지 않은 것
- **사용량**: 서비스가 센 토큰을 그 키의 이번 달 사용량에 더한다.

## 5. 제안

제안은 실행 하나가 만든 쓰기 항목의 묶음이다. 대화에 속하고 서버에 저장된다.

```ts
type Proposal = {
	id: string;
	runId: string; // the conversation run that made it
	request: string; // the admin's words, quoted on the review page and in the activity log
	status: "pending" | "applying" | "applied" | "partial" | "reverted" | "discarded";
	groups: { kind: string; label: string; itemIds: string[] }[]; // "다듬기 · 발행 후 고친 글 · 3곳"
	items: ProposalItem[];
};

type ProposalItem = {
	id: string;
	operation: string; // "entries.moveToFolder"
	input: unknown;
	target: { kind: "entry" | "media" | "tag" | "settings" | "schema"; id?: string; spot?: string };
	preview: { before: unknown; after: unknown };
	base: string; // version or hash of the spot when the item was made
	included: boolean; // the admin can leave it out
	state: "pending" | "stale" | "accepted" | "applied" | "failed" | "reverted" | "kept"; // kept: not reverted because it changed since
	reason?: string; // shown with a failed, stale or kept item
	undo?: unknown; // what reverting needs, written when applied
	thread?: SpotRequestThread; // section 7
};
```

### 화면에 보이는 상태

| 상태 | 카드 | 지난 대화 행 |
|---|---|---|
| 검토 대기 | "4묶음 · 16건 · 검토 대기" · 상세 보기 · 버리기 · [16건 적용] | "검토 대기" |
| 적용 중 | 검토 화면에 "적용 중 9 / 14" | — |
| 적용됨 / 일부 못 함 | "✓ 13건 적용 · 1건 못 함 · 10:52 · 모두 되돌리기", 못 한 항목과 이유 | "적용 13건" |
| 편집기에서 받음 | — | "받음 5곳" |
| 되돌림 | "되돌림 · 10:44" | "되돌림" |
| 버림 | 흐려지고 "버림" | "버림" |

- 검토 대기인 제안은 따로 만료되지 않는다. 대화가 남아 있는 동안 유효하고, 대화와 함께 지워진다("안 연 대화 N일 뒤 지우기" 설정).
- 카드의 건수는 검토에서 뺀 항목과 그사이 바뀐 항목을 따라 줄어든다(16 → 14 → 13).

### 어디에 보이나

| 무엇 | 보이는 곳 |
|---|---|
| 열린 글의 본문과 필드 | 편집기 안의 파란 연필 표시(9절) |
| 여러 글, 목록 전체, 태그 | 대화 안의 제안 카드. "상세 보기"를 누르면 검토 화면이다. 검토 화면에는 "한 줄 / 나란히" 보기, 항목마다의 체크, 묶음마다의 "모두 빼기", 본문 묶음의 "편집기에서 보기"가 있다 |
| 미디어 여러 장의 대체 텍스트 | 타일 위의 파란 제안과 "제안 3 · 모두 버리기 · 모두 받기". 같은 내용이 패널 카드에도 있다 |
| 설정 | 설정 화면의 저장 안 한 변경. 파란 표시, 칸마다의 "버리기", "모두 되돌리기", [저장하고 적용]이 있다 |
| 스키마 | 필드 목록의 "✦ 제안". 배포된 사이트에서는 저장이 PR이 된다 |

### 그사이 바뀐 자리

- 검토 화면을 열 때와 적용할 때, 항목마다 `base`를 지금 상태와 비교한다.
- 다르면 그 항목은 "이 사이에 고쳐짐"이 되고 저절로 빠진다. 사람이 쓴 것을 덮어쓰지 않는다.
- "다시 만들기"는 같은 대화에서 그 항목만 지금 상태로 다시 만드는 작은 실행이다. 새 항목이 옛 항목을 바꾼다.

## 6. 적용과 되돌리기

**적용**
- 포함된 항목을 순서대로 하나씩 `apply`한다.
- 항목마다 결과를 바로 저장한다. 그래서 중간에 끊겨도, 이어서 적용하면 남은 것만 한다.
- 항목들을 묶는 트랜잭션은 없다. 하나가 실패해도 나머지는 계속하고, 실패는 이유와 함께 남는다("못 옮김 · 그 사이 휴지통으로 감").
- 진행은 검토 화면과 카드에 흐른다("적용 중 9 / 14").
- 다 되면 활동 기록에 한 줄이 남는다(10절).

**되돌리기**
- 세 곳에서 할 수 있고, 셋 다 같은 동작이다.
  - 카드의 "모두 되돌리기"
  - 활동 기록의 "되돌리기"
  - 편집기 ⋯ › "AI가 바꾼 기록"
- 항목마다 `undo` 정보로 되돌린다.
- 적용한 뒤 사람이 그 자리를 또 고쳤으면(`base`가 적용 직후와 다르면), 그 항목은 되돌리지 않고 "그 사이 고쳐짐"으로 남긴다. 나머지만 되돌린다.
- 휴지통으로 보낸 것은 휴지통에서 꺼내는 것으로 되돌린다.

**버리기**
- 제안은 "버림"이 되고, 항목은 아무것도 바꾸지 않는다.
- 바뀐 것이 없으므로 활동 기록에는 남지 않는다.

## 7. 그 자리에 대고 다시 요청

- 편집기의 파란 연필을 누르면 열리는 카드 "요청 · 문단 1"에서, 그 제안 한 곳에 대고 다시 고쳐 달라고 말한다("끝은 원래대로 두고 앞만 줄여 줘"). 미디어 타일의 대체 텍스트 제안도 같은 카드다. 이 문서는 이것을 "자리 요청"이라 부른다.
- 검토 화면의 항목에는 자리 요청이 없다. 검토 화면은 보고 넣고 빼는 곳이다. 다시 고치려면 "편집기에서 보기"로 그 글을 열어 거기서 요청한다.
- 자리 요청 하나가 작은 실행 하나다.
  - 맥락은 그 자리, 그 항목, 그 카드의 스레드다.
  - 에이전트는 같은 자리를 다시 고친다. 새 항목이 옛 항목을 그 자리에서 바꾸고, 스레드는 남는다.
- 여러 자리 요청이 함께 돌 수 있다. 상태 막대에 "요청 2 · 1 고치는 중"으로 보인다.
- 고른 글자에 남기는 요청은 서식 카드의 "요청 ⌘J"로 시작한다. 여백에 표시와 개수가 붙는다.

## 8. 빠른 작업 (바로 넣기)

- 칸 하나의 "✦ 채우기"가 쓰는 길이다.
  - API 키 화면에서 고른 빠른 작업 모델을 한 번 부르고, 정해진 모양의 답을 받는다.
  - 루프도, 도구도, 대화 저장도 없다.
- 맥락은 그 칸의 정의(설명, 제한), 글의 내용, 글 쓰는 방식이다.
- 결과는 브라우저에서 편집 중인 값에 바로 들어간다.
  - 저장 전이므로 ⌘Z가 되돌린다.
  - 저장 기록은 사람이 저장한 것과 같다.
- 작업 목록은 정해져 있다: 요약, 태그 추천, 시리즈 추천, 이미지 대체 텍스트, 캡션, 주소. 관리자가 고치는 프롬프트나 사용자 정의 작업은 없다.
- 버튼은 언제나 칸 하나를 채운다. 할 일 목록에서도 칸 하나인 줄(요약)만 줄 끝에 "✦ 채우기"가 있다. 여러 개를 다루는 줄(이미지 2개)은 그 자리로 가는 줄이고, 거기서 칸마다 채운다.

## 9. 편집기와 제안

- 열린 글을 고치는 항목은 편집기 안에 파란 연필 표시로 보인다. 지운 것과 넣은 것이 함께 보인다.
- 아래 말풍선 하나가 그 글의 모든 표시를 묶는다.
  - "↑ 1/5 ↓"는 모든 표시를 차례로 오간다.
  - 말풍선의 이름("더 짧게 다듬기")은 지금 표시가 속한 요청을 따른다.
  - "모두 버리기 · 모두 받기"는 그 글의 표시 전부에 적용된다.
- 표시를 누르면 카드가 열린다. 카드에는 그 항목 하나의 "버리기 · [받기]"와 자리 요청이 있다.
- 받은 항목은 편집 중인 글에 들어간다.
  - 저장하면 그 저장이 활동 기록에 "어시스턴트 제안 · 첫 번째 글 · 본문 5곳"으로 남고, 되돌릴 수 있다.
  - 지난 대화 행에는 "받음 5곳"이 붙는다.
- 필드 항목은 속성 창의 그 칸에 파란 표시로 보이고, 탭에 "AI 제안 있음" 점이 붙는다.
- 다른 글을 고치는 항목은 검토 화면의 "편집기에서 보기"로 그 글을 열면 같은 방식으로 보인다.
- 번역 채우기와 "✦ 다시 번역"도 이 방식이다. 블록 여러 곳을 바꾸므로 제안이다.

## 10. 활동 기록

- 적용된 제안은 ✦가 붙은 한 줄로 남는다. 줄에는 이런 것이 들어간다.
  - 요청 인용
  - 무엇이 얼마나 바뀌었는지("13건 · 다듬기 3곳 · 요약 1편 · 폴더 이동 9편")
  - "대화" 링크와 "되돌리기"
- 되돌리면 그 줄에 "되돌림 · 10:44"가 붙는다.
- 종류 필터의 "AI 제안"으로 이 줄만 본다. 편집기 ⋯ › "AI가 바꾼 기록"은 그 글로 거른 목록이다.
- AI 제안으로 설정을 저장한 것도 ✦ 줄로 남고, 이전 값으로 되돌릴 수 있다. 배포 사이트의 스키마 변경은 PR이므로, 줄은 남지만 되돌리기는 없다.
- 모든 변경에는 행위자("누가")가 남는다. 에이전트가 한 일은 실행을 시작한 관리자와 대화 id를 함께 남긴다. 휴지통의 "✦ 버림"과 그 대화 링크가 이것을 읽는다.

## 11. 보안

- 도구는 실행을 시작한 관리자의 권한과 검사로 돈다. 화면의 요청과 같은 가드를 거친다.
- 쓰기는 언제나 제안이다. 사람이 받기 전에는 바뀌지 않는다(원칙 4).
- 다음은 도구로 만들지 않는다: 영구 삭제, 비우기, 비밀값과 키 읽기, 관리자 계정에 관한 일.
- 도구 결과는 길이를 자른다. 같은 도구를 같은 입력으로 거듭 부르면 막는다.
- 키 값은 모델에도 화면에도 보내지 않는다.
