# 화면 명세

화면을 데이터(`*.screen.json`)로 적고, `@monti-cms/ui`의 `ScreenSpec`이 디자인 시스템 부품으로 그린다. 명세가 중심이고, 명세의 모양은 디자인 도구를 따르지 않는다. 시안을 명세로 바꾸는 변환기는 없앴다. 명세는 사람이(또는 AI가) 디자인 시스템 부품으로 직접 적는다. 렌더러는 생김새와 배치만 그린다. 동작은 나중에 요소 id와 카탈로그의 `events`에 붙인다. 지금은 로그인 첫 상태와 글 목록 첫 상태로 시범 중이다.

목표는 시안과 같은 **배치**다. 어느 부품이, 어떤 순서로, 어느 묶음과 패턴의 칸에, 어떤 간격 토큰으로 놓이는지가 같으면 된다. 픽셀이 같은 것은 목표가 아니다. 시안은 "무엇이 어디에"의 기준이고, 시안에 우연히 적힌 숫자(열 너비 92px 같은 것)는 어디에도 옮기지 않는다.

## 도구와 팩

이 도구는 디자인 시스템 하나에 묶이지 않는다. 디자인 시스템마다 다른 것은 **팩** 하나에 모으고, 도구는 팩을 받아 똑같이 돈다.

- **도구(고정 프로그램):** 형식(`packages/ui/src/spec/format.ts`), 검사(`check.ts`), Spacing 변환(`spacing.ts`), 렌더러 뼈대(`render.tsx`의 `createScreenSpec`), 스크립트(`gen-screen-catalog`, `check:screens`). 디자인 시스템의 부품 이름, 클래스, 아이콘 세트를 하나도 적지 않는다. `pnpm check:screens`가 이것도 검사한다.
- **팩(디자인 시스템마다 하나):** Monti의 팩은 `packages/ui/src/spec-pack`이다.
  - `parts.tsx`: 명세가 쓸 부품, 각 부품과 prop의 종류(`CATALOG`), 간격 단계와 묶음이 될 배치 항목(`SCREEN`).
  - `spacing.ts`: 간격 단계마다의 클래스.
  - `index.tsx`: 팩으로 만든 렌더러(`@monti-cms/ui/spec`의 `ScreenSpec`).
  - `pack.mjs`: 스크립트 설정(명세가 있는 폴더, 카탈로그 위치).
- 팩을 만드는 일은 판단이 필요해서 AI가 맡는다(`.claude/skills/screen-pack`). 사람이 확인하면 그 디자인 시스템의 팩이 된다.

## 닫힌 것과 열린 것

- **닫힘(디자인 시스템만):** 부품과 그 variant, 색, 글자, 간격은 토큰으로만 쓴다. 빈 공간은 Spacing으로만 만든다.
- **열림(화면이 정하고, 그 화면의 명세에 적는다):** 화면 자신의 배치다. 영역의 너비(폼의 `maxWidth: 360` 같은 것), 가운데 정렬, 한 줄을 맨 아래에 붙이기, 어느 영역이 자라는지가 여기에 들어간다. 이 값은 배치용 컨테이너(`Stack`)에만 쓰고, 부품에는 쓰지 않는다. 빈 공간을 만드는 데도 쓰지 않는다.
- **거리와 배치:** 두 요소 사이, 또는 가장자리와 요소 사이의 거리는 Spacing이다(토큰만). 영역의 크기나 자리는 배치다. 배치 값은 `width`, `maxWidth`, `minWidth`, `align`, `justify`, `grow`, `direction`이고, 거리 값(margin, padding, top, left, offset)은 하나도 없다. 시안의 `position: absolute; bottom: 24px`는 "맨 아래에 붙이기"(위쪽 영역이 `grow`)와 끝 Spacing 24로 나뉜다. 토큰이 아닌 거리(200 같은 것)는 변환기가 "배치로 나타내거나 시안을 토큰으로 고칠 것"으로 알린다.
- 같은 배치가 두 화면 이상에 나오면 그때 디자인 시스템으로 올린다. 그 전에는 올리지 않는다. 아무도 디자인하지 않은 이름(패턴, 너비 토큰)을 미리 만들지 않는다.

## 형식

- 평평한 요소 표: `root`와 `elements`. 요소는 `type`(부품), `props`, `children`, `slots`(패턴의 칸, 요소나 글자), `visible`, `repeat`을 가진다.
- `repeat`: `{ "state": "/rows" }`의 항목마다 그 요소를 한 번씩 그린다. 그 안에서 `{ "item": "/title" }`이 항목의 값을 읽는다.
- 값: 그냥 값(선택지, 켬과 끔, 배치 숫자), `{ "state": "/경로" }`(화면의 상태에서 읽기), `{ "action": "이름" }`(페이지가 넘기는 동작).
- 글은 세 모양뿐이다: `{ "text": "login.or" }`(사전의 키, 한국어와 영어), `{ "template": "login.welcome", "values": { "name": "$user.name" } }`(값을 넣는 사전 글, 값은 `$상태.경로`나 반복 안의 `$item.경로`), `{ "state": "/user/email" }`(상태에서 읽기). 반복 안에서는 `{ "item": "/title" }`도 쓴다. 글을 명세에 직접 적지 않는다.
- HTML 속성(id, 입력칸의 name, 주소)은 명세에 하나도 없다. 라벨은 칸을 명세 안의 요소 이름으로 가리킨다: `"props": { "for": "@emailInput" }`. 실제 `id`와 `htmlFor`는 그릴 때 만든다. 입력칸은 데이터에 `"bind": "/form/email"`로 잇는다. 이 이름이 보낼 때의 이름이 되고, 나중에 동작을 붙일 때도 쓴다. 폼 안의 버튼은 그 폼을 보낸다.
- `visible`: `{ "state" }`(값이 있으면 보임), `{ "not": … }`.
- `className`, `style`, 픽셀 숫자는 없다. 픽셀을 받는 prop(`Table.width`, `TableCell.size`, `ListHead.end`)은 카탈로그에 없다. 열 너비도 명세에 없다. 표는 `Table`의 기본 동작으로 너비를 정한다(열은 내용 너비, 줄여 쓰는 제목 열이 남은 자리). 그 기본이 틀려 보이면 명세가 아니라 `Table`을 고친다. 사람이 끌어서 바꾼 너비는 실행 중의 데이터이고 명세 밖이다.
- 데이터로만 채우는 prop: 목록이나 객체를 받는 prop(열 이름, 쪽 크기 선택지)은 `{ "state" }`로만 받고, 항목은 `CATALOG`가 `data:` 종류로 정한 필드만 가진다. 보이는 것만 담고 생김새는 담지 않는다. 너비나 색 같은 필드가 오면 그리지 않고 멈춘다.
- 아이콘은 디자인 시스템 아이콘 목록(`packages/ui/src/icons.ts`의 `iconsByName`)의 이름으로만 고른다: `{ "type": "Icon", "props": { "name": "overflow-menu--horizontal" } }`.
- `Stack`은 방향과 화면의 배치(`align`, `justify`, `grow`, `maxWidth`, `minHeight: "screen"`)만 가진다. 배치는 빈 공간을 만드는 길이 아니다.
- 선은 디자인 시스템의 선 부품 `Box`(`border`만, `bottom-contrast`는 제목 아래 잉크 선)로 그린다.

## 빈 공간: Spacing

- 빈 공간은 컨테이너(`Stack`) `children` 안의 `{ "spacing": 20 }` 하나로만 쓴다. 크기는 간격 토큰(2·4·6·8·10·12·16·20·24·32·40·48)만 된다.
- 두 요소 사이에 있으면 그 사이 간격, 맨 앞이나 맨 끝에 있으면 컨테이너 축의 안쪽 여백이다. 두 개를 연달아 쓰지 않는다.
- 축은 컨테이너 방향이 정한다(`column`은 높이, `row`는 너비). 옆 여백은 패턴이 고정값으로 가진다. 패턴이 없는 한 번뿐인 상자는 방향이 다른 두 `Stack`을 겹쳐 쓰고, `ScreenSpec`이 한 요소로 합친다(`px-monti-24 py-monti-16`).
- 사이 Spacing은 뒤 요소와 함께 숨는다.
- 그릴 때 토큰 클래스로 바뀐다: 맨 앞·끝은 컨테이너의 padding, 사이가 모두 같으면 컨테이너의 gap, 아니면 다음 요소의 margin. 빈 칸 요소는 없다.
- 부품은 바깥 여백을 갖지 않는다. 되풀이되는 컨테이너의 여백은 부품이 가지고, 다른 여백은 부품의 variant가 된다.

## 종류 (`CATALOG`)

팩의 `parts.tsx`(Monti는 `packages/ui/src/spec-pack/parts.tsx`)의 `CATALOG`가 항목마다 종류를, prop마다 종류를 정한다. 종류가 없는 prop은 TypeScript 타입에 있어도 명세에 쓸 수 없다(기본 금지). 부품이나 prop을 더하는 일은 그 종류, 곧 "디자인 시스템이 정하나, 화면이 정하나"를 정하는 일이다.

- 항목: `part`(생김새는 디자인 시스템이 정한다) 또는 `layout`(화면이 배치하는 컨테이너, 지금은 `Stack`).
- `variant`: 부품의 생김새 선택지. 디자인 시스템이 정한다.
- `flag`: 부품의 켬과 끔.
- `layout`: 배치 컨테이너의 방향, 정렬, 자람. `layout` 항목에만 있다. 화면이 정한다.
- `layout-number`: 영역의 크기(px, `maxWidth`). `layout` 항목에만 있고, 부품에 두면 카탈로그가 만들어지지 않는다. 거리가 아니다.
- `event`: 함수. 명세에는 쓰지 않고, 나중에 요소 id로 붙인다.
- `data`: 데이터로만 채우는 목록이나 객체와, 항목이 가질 수 있는 필드.
- `text`: 화면에 보이는 글(라벨, 안내 글). 사전이나 데이터에서 온다.
- `ref`: 명세 안의 다른 요소(`@emailInput`). 라벨이 가리키는 칸.
- `state`: 상태에서만 오는 값(그림의 주소).
- `action`: 화면이 하는 일의 이름(`{ "action": "signIn" }`).
- 항목의 `only`: 그 항목이 설 수 있는 자리의 전부다. 다른 항목의 이름 붙은 칸으로 적는다(`["PageFrame.banner"]`). 자리가 화면이 정할 것이 아닌 부품에 준다. Monti의 팩에서는 `Banner`다: 틀(`PageFrame`)의 띠 자리(`banner`)에만 서고, 다른 곳(페이지의 `children`, 다른 부품의 칸, 화면의 `root`)에 적으면 `check:screens`가 막는다. 코드에서 `check:design`의 `banner-place`가 지키는 것과 같은 규칙이다(T150).
- 필수 prop: 부품의 타입에서 `?`가 없는 prop은 명세에 꼭 있어야 한다(카탈로그의 `required`). `Banner`의 `title`이 그렇다: 문장 없는 띠는 그려지지 않는다.
- 항목의 `bind: "yes"`: 그 항목은 요소의 `bind`(보내는 데이터)를 받는다. 입력칸, 검색, 쪽 크기 메뉴.

생성 스크립트는 정한 종류를 실제 타입과 맞춰 본다. 선택지가 아닌 타입에 `variant`를 주거나, 부품에 `layout-number`를 주거나, 없는 prop을 적으면 멈춘다.

`minHeight`는 이름 붙은 값 하나, `"screen"`(창 높이만큼)만 받는다. 혼자 선 화면에서 맨 아래 줄을 붙일 때 쓴다.

## 카탈로그와 검사

- `pnpm gen:screen-catalog`가 `CATALOG`와 부품들의 실제 prop 타입을 읽어 팩의 `catalog.generated.json`을 만든다. 선택지는 타입의 유니언 그대로다.
- `pnpm check:screens`(CI)는 모든 `*.screen.json`을 검사한다. 없는 부품, 없는 prop, 없는 값, 없는 칸, 빠진 필수 prop, 제자리(`only`) 밖에 선 부품, 토큰 밖 Spacing, 연달은 Spacing은 요소와 자리를 적고 실패한다.
- `ScreenSpec`은 json-render처럼 브라우저에서만 그리거나 실행 중에 화면을 만들지 않는다. 그리기 전에 같은 검사를 하고, 문제가 있거나 사전에 없는 글자 키, 페이지가 주지 않은 동작이 나오면 멈춘다. 몰래 건너뛰지 않는다.

## 동작

- 함수를 받지 않은 부품은 생김새만 그린다(행 체크, 쪽 크기 메뉴, 검색 버튼). 부품의 함수 prop은 그래서 모두 선택이다.
- 카탈로그는 부품마다 함수 prop을 `events`로 적는다. 동작은 요소 id와 이 이름으로 붙인다.

## 확인

- 구조 비교: 같은 부품, 같은 순서와 묶음, 같은 패턴 칸, 같은 간격 토큰인지 본다. 다르면 자리와 함께 적는다. 예: "Stack › Form › Stack[4]: 시안에는 Separator가 있고 명세에는 없다".
- 크기와 높이 차이는 비교하지 않는다. 끝에 사람이 한 장으로 전체 모습을 한 번 본다.

## 서버

`ScreenSpec`은 hook과 context가 없는 함수라 서버 컴포넌트에서 그린다. 브라우저에서 도는 코드는 각 부품 안에만 있다.
