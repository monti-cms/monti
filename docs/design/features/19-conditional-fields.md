# 19 조건부 필드

상태: 엔진을 만드는 중 (2026-11-13). 화면은 소유자가 목업을 본 뒤에 만든다.

소유자 (2026-11-13): "조건부 필드는 만들어야할 듯? 핵심 기능이라", "난 keystatic의 조건부 필드 생각했는데".

## 한 문장

고르기의 값에 따라 그 선택지의 필드들이 보이고, 고른 선택지의 값만 남는다.

## 모양

필드 종류 `conditional`이다(Keystatic의 `fields.conditional`, 옛 CMS의 `conditional`과 같은 생각). 고르기 하나와, 선택지마다 필드 묶음 하나를 가진다. [01](01-content-structure.md)의 원칙 5는 "필드 종류는 다섯 가지"가 된다.

```ts
format: {
	kind: "conditional",
	required: true,
	options: ["article", "video", "link"],
	fields: {
		video: { videoUrl: { kind: "text", required: true }, poster: { kind: "media", accept: "image" } },
		link: { linkUrl: { kind: "text", required: true } },
		// article에는 묶음이 없다: 고르면 더 채울 것이 없다.
	},
},
```

## 만들며 정함 (2026-11-13)

- **저장은 납작하다.** 글의 값에는 고른 선택지가 그 필드 이름(`format: "video"`)으로, 묶음의 필드가 제 이름(`videoUrl`)으로 다른 필드 옆에 든다. 옛 CMS와 같다. 값을 읽고 쓰는 곳(목록의 열, 찾기, 관계, 미디어 쓰임, 번역, 읽기 뷰)이 모두 필드 이름 하나로 값을 찾으므로, 납작하면 그 코드를 그대로 쓴다. Keystatic은 `{ discriminant, value }`로 겹쳐 저장한다: 그 모양은 사이트가 `values.format.value.videoUrl`로 읽게 하고, 위의 곳을 모두 고쳐야 한다.
- **필드 이름은 컬렉션 안에서 하나다.** 묶음이 달라도 같은 이름을 쓸 수 없다(납작하게 저장하므로). 겹치면 "고칠 곳"이다.
- **고른 선택지의 값만 남는다(레퍼런스: Keystatic).** `entries.save`와 `entries.create`가 저장할 때 다른 선택지의 값을 뺀다. 숨은 값을 데이터베이스에 남겨 두고 사이트에 낡은 값을 주는 제품(Payload, Sanity, Strapi, ACF)의 문제를 피한다.
- **필수는 고른 선택지 안에서만 필수다.** 발행 전 할 일도 같다. 고르기 자체가 필수면 고르지 않은 글은 할 일에 오른다. 스키마에서 빠진 선택지를 쥔 글은 고르지 않은 글로 본다.
- **지워질 값은 지워지기 전에 보인다(Keystatic보다 더 한다: Keystatic은 알리지 않는다).** Monti에서는 사람이 보지 못한 채 사라지는 값이 없다. 화면은 선택지를 바꾸면 "저장하면 n개 값이 지워집니다"를 보이고(화면 조각), 엔진은 고르지 않은 선택지의 필드에 값을 적어 보낸 저장을 그 필드 이름과 함께 거절한다(`entries.notChosen`). 조용히 버리지 않는다.
- **구조를 바꿀 때.** 계획은 저장되는 필드 이름으로 견준다. 선택지를 빼면 그 묶음의 필드가 빠지는 필드로 검토에 오르고("값 지우기" / 다른 필드로 옮기기), 그 선택지를 고른 글의 수가 고르기의 변경 줄에 보인다. 필드를 묶음 사이로 옮기거나 있던 필드들을 조건부 필드로 묶는 것은 이름이 그대로라 값이 남는다(고르지 않은 선택지의 값은 그 글을 다음에 저장할 때 빠진다). 선택지 이름 바꾸기는 빼고 더하는 것이다(고르기 필드도 그렇다).
- **T195.** 고르지 않은 선택지의 필드에 대한 제안은 적용할 때 위의 거절을 받는다(적용은 `entries.save`를 부른다). `entries.compare`는 초안에서 고르지 않은 선택지의 필드를 "다른 곳"으로 세지 않는다. 편집기와 검토 화면에서 그 제안이 어떻게 보이는지는 화면 조각에서 정한다.

## 지금은 하지 않는 것

- 묶음 안의 조건부 필드(Keystatic은 된다), 묶음 안의 주소(`slug`), `title`과 `slug`를 조건부로 만들기: "고칠 곳"으로 거절한다.
- 체크박스로 고르기(Keystatic의 `checkbox` 판별값). 여러 개 고르기(`many`)도 없다: 고르기는 하나다.
- 번역 글은 저장할 때 값을 빼지 않는다. 고른 선택지는 원문의 것이라 번역 글의 값만으로는 알 수 없다(T184).
- 선택지를 뺄 때 그 선택지를 고른 글의 값을 다른 선택지로 옮기는 단계(T185).

## 화면 (목업 뒤에 만든다)

필드 시트(선택지와 선택지마다의 묶음), 필드 목록의 묶음 표시, 속성 패널(선택지를 바꾸기 전과 뒤, 지워질 값의 줄), 검토 시트의 줄, 숨은 필드에 대한 제안.

## 끝 조건

- **19-1** `conditional` 필드를 가진 스키마가 저장되고 읽힌다. 선택지에 없는 묶음, 겹치는 필드 이름, 묶음 안의 조건부 필드와 주소는 "고칠 곳"이다.
- **19-2** 저장하면 고른 선택지의 값만 남고, 사이트가 읽는 값과 목록의 열에도 그 값만 있다. 고르지 않은 선택지의 필드에 값을 적어 보낸 저장은 필드 이름과 함께 거절된다.
- **19-3** 필수는 고른 선택지 안에서만 발행을 막는다.
- **19-4** 선택지를 빼면 그 묶음의 필드가 검토에 오르고, 묶음 사이로 옮긴 필드는 값을 지킨다.
- **19-5** 고르지 않은 선택지의 필드에 대한 제안은 적용할 때 거절되고, 비교는 그 필드를 세지 않는다.
- **19-6** 화면: 필드 시트에서 조건부 필드를 만들고 고치고, 속성 패널에서 고른 선택지의 필드만 채운다(화면 승인 뒤).
  - 만든 것 (2026-11-13): 속성 패널(고른 선택지의 필드, 저장 전 "저장하면 … 값 n개가 지워집니다"), 필드 시트가 조건부 필드를 고르기 필드로 저장하지 않게 한 것(선택지의 필드를 그대로 둔다). 남은 것: 필드 시트와 필드 목록, 검토, 제안, 비교(목업 승인 뒤).
