Monti's core (`packages/core`) is being rewritten from scratch, and its design is `docs/refactor/core.md`. That document and what the owner says are the only authority. The old code, `docs/design/features` and the old tracker are gone and were wrong where they differ: do not rebuild anything from memory of them. The other documents in `docs/refactor` say what goes to the other packages and are worked on only after the core. Before any work, read the stage you are in (core.md, "작업 방식"). The acceptance conditions are in `docs/acceptance/<pkg>/` and are read-only for you; how they are written and how tests link to them is in `docs/acceptance/README.md`. Keep acceptance conditions concise and focused on required domain rules (do not pre-emptively inflate them with speculative edge cases; split large resources into cohesive slices). Before drafting acceptance conditions for any write or public entry point, check the 4 concurrency & security questions in `docs/acceptance/README.md` and record applicable behavioral contracts under that resource's `경계 · 방어 검증` section. Each condition has one test whose title starts with its number, and you add nothing the conditions do not state; Stryker survivors are classified into 4 buckets (ignore meaningless/equivalent, delete unrequested branch, strengthen existing AC, or escalate new rule to the owner) — never delete a security or concurrency defense under bucket 2, escalate it to bucket 4 instead. Do not defer or shrink work: if something is blocked, too big, or a condition looks wrong, report it to the PM.

Docs under `docs/`, code comments, test titles and error messages are written in Korean: the owner reads and approves them and writes the code in Korean. Code names, file paths, tokens and commands in them stay as they are in the code. Commit messages and PR titles and descriptions are in English (commitlint enforces it). A `README.md` stays in English with its `README.ko.md` in Korean; when a `README.md` changes, update its `README.ko.md` in the same change. English comments and titles already in the code stay as they are until that code is touched.

Commit messages and PR titles follow Conventional Commits (`type(scope): subject`). The scopes are in `commitlint.config.mjs`; a new package adds its own.

Prefer LSP for symbol navigation, references, types, rename and diagnostics.
